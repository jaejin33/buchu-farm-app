2026년 10월 25일 기준. 1단계(현장 파악) 1·2차 설문 완료. 앱은 6단계(Supabase 로그인·동기화)까지 만듦 (6-6: 이력에 입력한 사람, "미전송 N건 · 마지막 동기화"). 5.5단계(아버지 시험)는 아버지 의견을 기다림. 다음은 push → 형 폰 설치, 두 폰으로 확인. 6단계 다음 할 단계는 아직 정하지 않음.

## 현재 상태

- 현장 파악: 1·2차 설문 완료. 영농일지 사진, 아버지 통화는 아직 (질문하기 어려운 상황이라 개발자가 아는 선에서 답해 3단계 설계를 정함)
- 앱: 1·2단계, 2.5·2.6·2.7단계, 3·4·5·5.1·6단계 완료. 테스트 106개 통과
- 사용자 폰: 아버지는 갤럭시(안드로이드 크롬), 형과 개발자는 아이폰(사파리). **두 폰 모두 동작해야 한다** ([[결정기록]] 2026-10-23)
- 사용자는 아버지와 형뿐. 일하는 분들은 지금 사용자가 아님 (업무 일정·알림 기능이 생기면 대상이 될 수 있음). 가입은 열지 않고 계정은 개발자가 만듦 ([[결정기록]] "가입은 열지 않는다", "일하는 분들은 지금 사용자가 아니다")
  - 하우스 목록: 수확 후 N일, 약 후 N일, 🟢 수확 가능(수확 기록의 `cycle_days`가 지나면). 약 대기 자동 판단은 없앰 ([[결정기록]] 2026-10-22)
  - 수확 중: "수확 시작" → "수확 완료" 두 기록. 시작 당일 "오늘 시작", 다음 날 "시작 후 N일". 하루에 끝나면 완료만 눌러도 됨. 수확량은 완료 다음 날 합계 한 번 (한 동은 길어야 2일)
  - 하우스 문제(💧 배수 불량, 🍄 균사 많음)는 `problem` 기록(생김/해결됨)으로 남김. 처음엔 모든 동 이상 없음
  - 구역 6개 반영 (1~4 / 5~10 / 11~13 / 14~16 / 17~20 / 21~25동)
  - 디자인: 토스 앱 느낌(연회색 바탕, 구역마다 둥근 흰 카드, 한 동 한 줄), 주 색 초록. 문제는 "💧 배수 불량", "🍄 균사 많음" 글자 배지. 기준 글자 크기 20px, 가장 작은 글자 16px 이상. 진짜 폰으로 확인함
  - 확인 필요: "배수 불량", "균사 많음"이 아버지가 쓰는 말과 맞는지
  - 남은 확인 (형): 구역을 부르는 이름
  - 기록 입력(3단계): 목록에서 동을 누르면 열림. 날짜(기본 오늘) → 약 / 웃거름 / 관비 / 수확(시작·완료·수확량) / 문제(생김·해결됨) → 저장. 약 이름은 안 적어도 됨, 지난 약은 버튼으로 고름. 저장하면 폰 안(IndexedDB)에 남고 목록이 바로 바뀜. 폰 뒤로 가기로 목록 복귀 ([[결정기록]] "기록 입력 화면 구성")
  - 가짜 기록은 지웠다. 앱은 기록이 하나도 없는 상태로 시작한다
  - 폰에서 http로 시험할 때 기록 id 문제는 해결함 (`crypto.getRandomValues`로 직접 만듦)
  - 이력(4단계): 기록 입력 화면 오른쪽 위 "지난 기록 ›"에서 열림. 그 동의 기록을 최근 순, 날짜별 카드로. 줄마다 [취소] → "이 기록을 취소할까요?" → 취소 기록 추가 ([[결정기록]] "잘못 입력한 기록은 이력 화면에서 취소", "이력 화면 구성")
  - 이력 줄마다 아랫줄에 입력한 사람 이름("아버지", "형", "개발자")이 보임 (6-6). 이름은 Supabase `profiles` 표에 개발자가 넣고, 폰은 주고받을 때마다 통째로 받아 둠(오프라인에서도 보임). 표에 없으면 "모르는 사람" ([[결정기록]] "입력한 사람의 이름은…", "개발자 계정의 이름은…", "이름 표는…통째로…", [[2026-10-23-6단계-코드-읽기]] 11번)
  - 화면은 PC 크롬 폰 크기(390px)로 눌러 가며 확인함. 10월 23일 진짜 폰으로 기록 입력 화면을 보다가 날짜가 두 줄로 꺾이는 것을 찾아 고침 (날짜 글자는 앱이 그리고 진짜 날짜 칸은 투명하게 덮음, [[결정기록]] 2026-10-23). 고친 뒤 폰에서 날짜·"바꾸기" 확인함. 이력 화면은 폰에서 따로 확인했다는 말은 없음
  - 배포(5단계, 10월 23일): Vercel에 GitHub 레포를 연결함. `main`에 push하면 자동 배포. http 주소에서는 PWA 기능이 막히고 개발자 폰이 아이폰이라, 원래 7단계였던 배포를 앞당김 ([[결정기록]] 2026-10-23, [[2026-10-23-https와-Vercel-자동-배포]]). push 전에 `npm test`, `npm run build`
  - 배포 뒤 PC에서 날짜 상자가 안 눌리던 것을 고침 (PC 크롬은 달력 아이콘을 눌러야만 열려서, 마우스 기기에서는 앱이 직접 엶). PC 보통 화면에서 확인함. F12 폰 크기 보기에서는 여전히 안 열릴 수 있음 ([[2026-10-23-날짜-칸-덮기와-클릭-이벤트-전파]] 5번)
  - PWA(5.1단계): 홈 화면에 추가("부추 하우스", 초록 바탕 흰 부추 잎 아이콘), 인터넷이 끊겨도 열림. 새 버전은 다음에 열 때 뜸(입력 중 화면이 바뀌지 않게). PC 크롬 오프라인과 아이폰에서 확인함. 아버지 갤럭시에 설치함(10월 23일, 개발자). 갤럭시에서 오프라인으로 열리는지는 확인했다는 말 없음 ([[결정기록]] "PWA: 새 버전은 다음에 열 때 뜬다", [[2026-10-23-PWA와-서비스-워커]])
  - 5.5단계(아버지 시험): 따로 자리를 만들지 않고 아버지가 써 보시고 알려주시기로 함. 갤럭시 설치 확인도 그때
  - Supabase(6-1, 6-2): 무료 요금제, 서울 지역. 주소와 publishable 키는 `.env`(이 PC)와 Vercel 환경 변수에. `records` 테이블은 로그인한 사람만 조회·추가, 추가는 자기 이름으로만, 수정·삭제는 아무도 못 함(`supabase/records.sql`). 로그인 없는 요청이 막히는 것 확인. 가입 막기("Allow new users to sign up" 끔)도 가짜 주소 가입 요청이 `signup_disabled`로 막히는 것 확인 ([[2026-10-23-환경-변수와-Supabase-권한]])
  - 로그인(6-3): 이메일 + 비밀번호, 처음 한 번. 가입 화면 없음. 로그인하면 시험 기록(임시 입력자)을 지우고, 이후 기록은 로그인한 사람 이름으로 저장. 인터넷이 끊겨도 로그인 화면이 뜨지 않게 "누가 로그인했나"를 폰에 따로 적어 둠. 계정은 개발자, 아버지(10월 23일 만들어 아버지 폰에 로그인해 둠), 형(10월 23일 만듦, 형 폰 로그인은 아직) ([[2026-10-23-6단계-코드-읽기]])
  - 올리기(6-4, 10월 23일): `synced = 0`인 기록을 한 건씩 Supabase로 보내고 1로 바꿈. 저장 직후(기다리지 않음)·인터넷 재연결 때·앱 열 때 보냄. 같은 id가 이미 있다는 에러는 "이미 보낸 것", 다른 에러는 그 기록만 남겨 두고 다음 기록으로. 화면은 안 바뀜(표시는 6-6). 진짜 Supabase에 올라가는 것과 남의 이름 기록이 RLS에 막히는 것을 개발자가 PC에서 확인. ([[결정기록]] "올리기: 한 건씩 보내고…", [[2026-10-23-6단계-코드-읽기]] 8번, [[2026-10-23-JWT와-요청-인증]])
  - 시험 기록: 시험용 Supabase 프로젝트는 따로 두지 않음. PC에서 시험한 기록(개발자 계정)이 진짜 Supabase에 쌓이고, 아버지 폰이 새 버전을 받으면 아버지 폰에도 내려감. 그대로 두었다가 **제대로 쓰는 날 서버와 모든 기기를 한꺼번에 비운다** (서버에서 지워도 폰에 내려간 기록은 안 지워져서 기기도 비워야 함) ([[결정기록]] "시험 기록은 제대로 쓰는 날 서버와 기기를 한꺼번에 비운다")
  - 남이 입력한 기록도 취소할 수 있음 (지금 권한 그대로). 이렇게 둘지는 따로 정한 적 없음, 확인 필요 ([[2026-10-22-추가만-하는-기록과-취소]] 2번)
  - 내려받기(6-5, 10월 23일): 마지막으로 받은 시각(`received_at`)보다 5분 앞부터 서버 기록을 1000건씩 받아, 폰에 없는 id만 IndexedDB에 추가(`synced = 1`). 처음 받는 폰은 처음부터 다 받음. 앱 열 때·인터넷 재연결 때·**앱 화면으로 돌아올 때(새로 더함)** "올리기 → 내려받기". PC 일반 창·시크릿 창을 두 폰으로 보고 개발자가 확인 ([[결정기록]] "내려받기: 5분 겹쳐…", "앱 화면으로 돌아올 때도 주고받는다", [[2026-10-23-6단계-코드-읽기]] 9·10번, [[2026-10-23-시크릿-창으로-두-폰-시험하기]])
  - 6-5 시험 중, 6-4 RLS 시험 때 넣은 가짜 입력자 기록이 PC 일반 창에 남아 계속 거절(`42501`)되던 것을 찾아 지움. 코드 문제 아님

## 1. 농장 개요 (설문으로 확인된 사실)

- 비닐하우스 25동, 6곳 이상에 나뉘어 있으나 가장 먼 곳끼리도 이동 5분 이내
- 재배 기간 10월~4월, 가락동 농산물 도매시장에 거의 매일 출하
- 수확 철에는 아버지, 형 포함 10명 넘게 일함. 베트남 근로자를 고용 중
- 하우스 안 휴대폰 인터넷은 가끔 끊김
- 기록 방식: 수첩·공책(영농일지). 경매 정산서는 종이와 문자로 받음. 일당·시간 계산도 수첩에 기록
- 영농일지는 아버지가 혼자 관리하고, 형은 하루 작업을 아버지에게 보고한다

## 2. 작업 관리 현황

- 약: 한 달에 2~3번, 한 동씩 침. 아버지와 형이 직접 침. 수확 가능일은 약 봉투·설명서로 확인하며, 동마다 날짜가 달라 헷갈린 적이 가끔 있음. 헷갈리면 영농일지를 봄
- 비료: 밑거름(심을 때), 웃거름(벨 때마다 매번), 관비(한 달에 한두 번) 모두 함
- 수확: 한 동을 벤 뒤 다시 벨 때까지 30~40일
- 하우스별 차이: 배수가 안 되는 곳, 버섯균사 때문에 작물이 수분을 흡수하지 못하는 곳이 있음. 해당 하우스 6~10동. 농업기술센터 상담은 받은 적 없음. 고압 살수기로 땅을 파서 흙을 묽게 만드는 조치를 시도했고 결과 확인 중
- 경매 수수료: 응답은 0.7%. 일반적으로 알려진 위탁수수료 수준보다 낮아 보여 정산 문자로 확인 필요. 운송비는 미응답

## 3. 형의 주요 발언

- 시간이 제일 많이 드는 일: 수확, 약 치기, 비료 주기, 일하는 사람 관리
- 신경 쓰이는 일: 수확, 약 치기, 비료 주기, 하우스 관리
- "한 가지라도 소홀하면 수확량이 차이가 많이 난다. 귀찮은 건 아니지~"
- 바꾸고 싶은 것: 농장이 한곳에 모여 있으면 좋겠다
- "항상 가격이 좋을 수는 없고 연작 피해도 올 수 있으니 다른 작물도 공부해야 한다"
- 최근 실수로 손해 본 일: 없다고 응답

## 4. 인사이트와 결정 사항

- 앱의 가치는 "편하게 해준다"가 아니라 "25동을 빠짐없이, 고르게 관리하게 해준다"
- 이미 영농일지를 쓰고 있으므로, 새 습관을 만드는 것이 아니라 영농일지를 더 빨리 찾아보고 동마다 수확·약 후 며칠 지났는지 한눈에 보여주는 것이 핵심 (약 대기 자동 계산은 예외가 많아 빼기로 함, [[결정기록]] 2026-10-22)
- 작업은 "수확 → 웃거름 → 다음 수확 예정일"로 수확 주기에 묶여 돌아감
- 비료는 처음에 연 1회로 가정했으나 웃거름·관비가 있어 기록 필요
- 이동 시간이 문제라는 가설은 기각(5분 이내). 여러 곳을 동시에 관리하는 부담에 가까움
- 배수·균사 문제 하우스와 정상 하우스의 수확량 비교가 가장 가치 있는 분석 주제
- 형이 다른 작물을 고려 중이므로 데이터 구조에 "작물" 항목을 두고 부추에 한정하지 않음
- 인력: 고용 형태나 개인 정보는 기록하지 않음. 다른 농가용 서비스는 합법 고용(계절근로자 제도, 고용허가제 등)을 전제로 설계
- 언어 장벽: 베트남 근로자에게 작업을 정확히 전달하기 어려울 수 있음. 다국어 작업 지시 카드, 사진·영상 작업 가이드, 하우스 번호 표지판 등이 아이디어. 다만 농약은 아버지·형이 직접 치므로 가장 위험한 작업의 언어 위험은 상대적으로 낮음. 후순위로 보류하며 추가 확인 필요
- 영농일지는 아버지가 관리하므로, 앱에 누가 입력할지(아버지만 / 둘 다)가 설계에 중요한 질문. 확인 필요
- 개발 외 권고: 농업기술센터 토양 검정·병해 진단 상담

## 5. 사업 아이디어 (검토 중)

이익 = 수확량 × 단가 − 비용. 우리 농장 이익 개선(A)으로 시작해 효과가 확인된 것만 다른 농가 대상(B)으로 확장하는 순서.

- 하우스 관리 앱(작업·방제·수확 기록, 수확 가능일 표시): 현재 진행
- 출하 의사결정 도구(가락시장 경매 데이터, KAMIS, 기상 데이터 활용)
- 직거래·B2B 판로(식당, 반찬가게, 급식 등)
- 외국인 근로자 다국어 작업 지시·인력 행정 지원
- 스마트팜 센서·자동화, 가공·브랜딩

## 6. 기술 결정

세부 규칙(데이터 구조, 동기화, 화면)은 레포 루트의 `CLAUDE.md`가 기준이다.

- 형태: 네이티브 앱이 아닌 PWA(모바일 웹). 링크로 배포, 안드로이드·아이폰 모두 가능, 업데이트 즉시 반영
- 화면: React + TypeScript(Vite) + vite-plugin-pwa
- 폰 안 저장: IndexedDB(Dexie.js). 인터넷이 끊겨도 입력·조회가 모두 동작
- 서버: Supabase(PostgreSQL + Auth). 별도 백엔드 서버(Spring 등)는 당분간 쓰지 않음. 서버 교체에 대비해 Supabase 코드는 `src/data/` 안에만 둠
- 동기화: 기록은 수정·삭제 없이 추가만 함(잘못된 기록은 취소 기록 추가). 아버지·형이 오프라인에서 각자 입력해도 충돌하지 않음
- 수확 가능일 계산은 화면(프론트)에서 함. 오프라인에서도 계산되도록
- 테스트: Vitest. 수확 가능일 계산은 반드시 테스트와 함께
- 배포: GitHub → Vercel. `main`에 push하면 자동 배포 (5단계로 앞당겨 10월 23일 배포함)
- 분석: Python(pandas, scikit-learn), 데이터가 쌓인 뒤 Supabase의 PostgreSQL을 읽어 분석
- 로그인: 이메일 + 비밀번호. 계정은 Supabase 화면에서 직접 만들고 가입은 막음 ([[결정기록]] 2026-10-23)
- 시험: 시험용 Supabase 프로젝트를 따로 두지 않음. PC 개발 서버도 진짜 Supabase를 씀 ([[결정기록]] 2026-10-23)
- 요금: Vercel Hobby, Supabase Free 모두 무료 (2026-10 확인). Supabase 무료는 7일 동안 안 쓰면 프로젝트가 멈춤(화면에서 다시 켜면 됨, 그동안 앱은 폰 기록으로 동작)
- 백업: Supabase 무료 요금제는 자동 백업이 없음 (2026-10 확인). 백업 방법은 6단계 뒤에 정함 (하루 1회 내보내기 등 검토)
- 설치: 홈 화면 추가와 첫 로그인은 집에 갔을 때 직접 해드리기
- 참고: Vercel 무료 플랜은 개인·비상업 용도 조건이 있어 사업화 시 요금제 확인 필요

## 7. 프로토타입 범위

해결할 문제 하나: "25동 각각, 수확·약 후 며칠 지났는지와 수확 가능한지 한눈에 안다."
사용자: 아버지와 형, 각자 휴대폰. 화면은 아버지 기준으로 크게 만든다. 진짜 기록은 종이 영농일지에 계속 남기며 사용성을 검증한다.

화면 세 개.

- 하우스 목록: 25동을 한눈에. 동마다 수확 후 N일, 약 후 N일, 🟢 수확 가능(정해 둔 일수가 지남), ⚪ 수확 기록 없음
- 기록: 동을 누르면 약·웃거름·관비·수확·문제를 버튼 몇 번으로 입력. 약은 이름만, 안 적어도 됨 (지난 약 목록에서 고르기). 수확은 수확 가능까지 일수(기본 35일, 바꿀 수 있음). 수확량(박스·단)은 다음 날 아침에 입력
- 이력: 그 동의 지난 기록을 입력한 사람 이름과 함께 보기. 잘못 입력한 기록은 여기서 취소

하우스 속성: 번호, 위치(구역), 작물, 문제 상태(배수, 균사 등).

이번 범위에서 제외: 인력 관리, 번역, 가격 분석, 푸시 알림.

개발 단계(자세한 내용은 `CLAUDE.md`): 계산 로직 → 하우스 목록(가짜 데이터) → 경과 일수 방식으로 변경 → 기록 입력 → 이력 → 배포(앞당김) → PWA → Supabase 로그인·동기화. 아버지 시험은 따로 자리를 만들지 않고 아버지가 써 보시고 알려주시기로 함.
