# 시크릿 창으로 두 폰 시험하기

6-5(내려받기)를 PC 한 대로 시험한 방법이다. "아버지 폰"과 "형 폰"이 따로 기록하고 서로 받아 오는지 보려면 폰이 두 대 있어야 할 것 같지만, **크롬 일반 창과 시크릿 창**이면 된다. 시험하다 "원래 있던 기록 하나가 안 내려온다"는 일이 있었고, 그 원인을 찾아간 순서도 3번에 남긴다. 코드는 [[2026-10-23-6단계-코드-읽기]] 9·10번.

## 1. 브라우저 저장소는 "주소"마다, 창 종류마다 따로다

앱이 폰 안에 남기는 것은 두 군데다.

| 저장소 | 우리 앱이 넣는 것 |
|---|---|
| IndexedDB (`buchu-farm`) | 기록 전부, 기록마다 `synced` 0/1 → [[2026-10-22-IndexedDB와-Dexie]] |
| localStorage | 로그인한 사람(`buchu-farm:user`), 로그인 표(`sb-…-auth-token`), 마지막으로 받은 시각(`buchu-farm:last-received-at`) |

브라우저는 이 저장소를 **주소(origin)마다 따로** 둔다. origin은 `프로토콜 + 호스트 + 포트`다.

| 연 주소 | origin | 저장소 |
|---|---|---|
| `http://localhost:5173` (PC `npm run dev`) | `http://localhost:5173` | A |
| `http://192.168.0.10:5173` (같은 개발 서버를 폰에서) | `http://192.168.0.10:5173` | B (A와 다름) |
| Vercel 주소 (`https://…vercel.app`) | `https://…vercel.app` | C (A·B와 다름) |

그래서 PC의 localhost에 적은 기록은 폰의 Vercel 앱에 **저절로 보이지 않는다.** 서버(Supabase)를 거쳐야만 건너간다. 같은 코드라도 주소가 다르면 다른 폰인 셈이다.

**시크릿 창은 같은 주소라도 일반 창과 저장소를 나누지 않고 따로 쓴다.** 그리고 시크릿 창을 모두 닫으면 그 저장소가 지워진다.

| | 일반 창 | 시크릿 창 |
|---|---|---|
| IndexedDB, localStorage | 일반 창끼리 같이 씀 | 시크릿 창끼리 같이 씀, 일반 창과는 따로 |
| 창을 닫으면 | 남음 | 지워짐 (기록, 로그인, 마지막으로 받은 시각 모두) |

그래서 `localhost:5173`을 일반 창과 시크릿 창에 하나씩 열면 **빈 폰 두 대**가 생긴다.

- 일반 창 = 내 폰 (기록이 이미 쌓여 있음)
- 시크릿 창 = 새로 산 폰 (아무것도 없음, 처음 로그인)

같은 계정으로 로그인해도 된다. 내려받기는 누가 적었는지 가리지 않고 "이 폰에 없는 기록"을 가져오기 때문이다. 계정 둘(아버지·형)일 때만 다른 것은 RLS의 "자기 이름으로만 추가"인데, 그건 올리기에서 이미 확인했다.

**주의:** 시크릿 창을 닫았다 다시 열면 또 "새로 산 폰"이다. 다시 로그인하고 처음부터 다 받는다.

## 2. 6-5를 시험한 순서

1. 일반 창에 기록이 몇 개 있는 상태에서 시작한다 (전부 올라가 있어야 함)
2. 시크릿 창으로 `localhost:5173`을 열고 로그인한다 → 서버에 있는 기록이 **다 내려와야** 한다 (처음 받는 폰이라 처음부터)
3. 일반 창에서 기록을 하나 저장한다 → 저장 직후 올라간다
4. 시크릿 창 탭으로 돌아간다 → `visibilitychange` → 내려받기 → 3번 기록이 보여야 한다
5. 거꾸로 시크릿 창에서 저장하고 일반 창 탭으로 돌아가도 보여야 한다

탭을 바꾸는 것이 폰에서 "다른 앱 갔다가 돌아오기"와 같다. 둘 다 `visibilitychange`가 온다.

## 3. "원래 있던 기록이 안 내려온다"를 찾아간 순서

2번에서 시크릿 창에 기록이 대부분 내려왔지만 하나가 빠졌다. 기록은 **적은 폰 → 서버 → 받는 폰**으로 건너가니, 어디서 끊겼는지 앞에서부터 본다.

### ① 어디서 적은 기록인가

- **폰(Vercel 주소)에서 적었다면** 정상이다. 그때 폰 앱은 push 전의 옛 코드라 올리기가 없었다. 1번 표처럼 Vercel 앱의 저장소(C)는 localhost(A)와 따로라, 서버로 안 올라가면 건너올 길이 없다
- **이 PC 일반 창에서 적었다면** ②로

### ② 적은 창에서 그 기록이 올라갔나 (`synced`)

일반 창에서 F12 → Console에 붙여 넣는다.

```js
indexedDB.open('buchu-farm').onsuccess = (e) => e.target.result.transaction('records').objectStore('records').getAll().onsuccess = (ev) => console.table(ev.target.result.map((r) => ({ 동: r.house_no, 종류: r.type, 날짜: r.work_date, 입력시각: r.recorded_at, synced: r.synced })))
```

- `indexedDB.open('buchu-farm')`: 앱이 쓰는 IndexedDB를 연다. 앱은 Dexie로 감싸서 쓰지만, Console에서는 브라우저에 원래 있는 것을 바로 쓴다
- `.onsuccess = (e) => ...`: "열리면 이걸 해라"를 붙인다. Dexie의 `await` 대신 옛날 방식(콜백)이다. Java로 치면 `future.thenAccept(e -> ...)`
- `transaction('records').objectStore('records').getAll()`: `records` 표의 모든 줄. `db.records.toArray()`와 같다
- `.map((r) => ({ 동: r.house_no, ... }))`: 줄마다 보기 좋은 칸만 골라 새 객체로 바꾼다. Java의 `stream().map(r -> new Row(...))`. 화살표 함수가 객체를 바로 돌려줄 때는 `({ ... })`처럼 괄호로 감싼다 (괄호가 없으면 `{`를 함수 몸통의 시작으로 읽는다)
- `console.table(...)`: 배열을 표로 찍는다

결과로 판단한다.

| 본 것 | 뜻 | 다음 |
|---|---|---|
| 그 기록이 `synced: 0` | **올리기에서 막혔다** | ④ |
| 다 `synced: 1` | 올라갔다고 표시됨 | ③ |

### ③ 서버에 있나

Supabase 화면 → Table Editor → `records`의 줄 수를 본다.

| 본 것 | 뜻 |
|---|---|
| 서버에 없음 | 올라간 것으로 **잘못 표시**됐다 (올리기 코드 문제) |
| 서버에 있는데 시크릿 창에 없음 | **내려받기 문제** |

### ④ 왜 막혔나: Console 경고 읽기

Console을 연 채로 새로고침(F5)한다. 앱을 열 때 안 보낸 기록을 다시 보내므로, 막히면 경고가 다시 찍힌다.

```
POST https://….supabase.co/rest/v1/records 403 (Forbidden)
기록 올리기 실패 1ffb2d8d-… {code: '42501', message: 'new row violates row-level security policy for table "records"'}
```

| `code` | 뜻 | 이 앱에서 흔한 원인 |
|---|---|---|
| `42501` | 권한 거절 (RLS, HTTP 403) | 기록의 `recorded_by`가 로그인한 사람이 아님 |
| `23505` | 같은 id가 이미 있음 | 경고가 안 뜬다. 앱이 "이미 보낸 것"으로 처리 |
| `PGRST…`로 시작 | Supabase 창구(PostgREST)의 에러 | 없는 칸 이름을 보냄 등 |
| 경고 없이 계속 0 | 보내지도 않음 | 인터넷 끊김(`navigator.onLine`), 로그인 표를 못 받음 |

`42501`이면 그 기록의 `recorded_by`와 로그인한 사람 id(`buchu-farm:user`의 `id`)를 견준다. **앞자리만 보고 같다고 하지 말고 끝까지 본다.** UUID는 `00000000-0000-…`처럼 앞이 비슷한 값이 많다.

### 실제로는

④에서 `42501`이었다. 6-4에서 RLS를 시험하려고 일부러 가짜 입력자(`00000000-0000-4000-8000-000000000001`)로 넣은 1동 웃거름 기록이 지워지지 않고 남아 있었다. 앱을 열 때마다 보내고, 서버는 매번 막았다. 가짜 입력자 기록만 지우는 코드를 Console에서 다시 실행해 지웠다.

- **코드 문제는 아니었다.** 권한이 막아야 할 것을 막았고, 한 건이 막혀도 다른 기록은 계속 올라갔다 ([[결정기록]] "올리기: 한 건씩 보내고…")
- 6-6에서 "미전송 N건"을 화면에 띄우면, 이런 기록이 있을 때 숫자가 줄지 않아 바로 드러난다

## 4. Console에 코드 붙여 넣기 주의

- 크롬은 처음 붙여 넣을 때 막고 `allow pasting`을 직접 치라고 할 수 있다. **남이 준 코드를 그대로 붙이게 해서 로그인 표를 훔치는 수법**이 있어서다
- 무엇을 하는 코드인지 알고 붙인다. 이 노트의 코드는 기록을 읽기만 하거나, 정해 둔 가짜 입력자 기록만 지운다
- Console에 찍힌 로그인 표(`sb-…-auth-token`의 값)는 다른 사이트나 채팅에 붙이지 않는다. 그 값만 있으면 비밀번호 없이 1시간 동안 그 사람으로 요청할 수 있다 → [[2026-10-23-JWT와-요청-인증]]

## 5. Spring·Java에서 비슷한 것

| 이 앱 | Spring 쪽 |
|---|---|
| 시크릿 창 = 새 폰 | 쿠키가 없는 새 클라이언트. Postman의 다른 환경, 다른 브라우저로 같은 서버에 로그인해 세션 두 개 만들기 |
| 저장소가 origin마다 따로 | 쿠키가 도메인마다 따로인 것 (`JSESSIONID`는 `localhost`와 운영 도메인에서 서로 안 보임) |
| Console에서 IndexedDB 직접 읽기 | H2 콘솔이나 DB 클라이언트에서 `select * from records`를 직접 쳐 보기 |
| `synced`로 어디서 끊겼는지 보기 | 메시지 큐 "보낸 쪽 → 브로커 → 받는 쪽"을 앞에서부터 확인하기 (아웃박스 테이블의 전송 여부 칸) |
| `42501` | 메서드 보안(`@PreAuthorize`)에 걸려 `AccessDeniedException` → 403 |

다른 점: Spring은 서버 하나에 클라이언트 둘이면 끝이지만, 이 앱은 **폰마다 자기 DB(IndexedDB)를 들고 있다.** 그래서 "서버에 있나"와 "그 폰에 있나"를 따로 봐야 한다. 서버 DB만 보면 되는 Spring과 달리 3번처럼 두 곳을 차례로 본다.
