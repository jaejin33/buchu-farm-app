# Vitest 테스트와 순수 함수

앱 1단계 `src/domain/harvestCalc.ts`(경과 일수와 수확 가능 계산)와 `harvestCalc.test.ts`에서 쓴 방식이다. 예시 코드는 2.5단계 기준이다. Java·Spring을 아는 입장에서 정리한다.

## 0. 먼저: 프로젝트를 움직이는 도구들

| 프론트 (이 프로젝트) | Spring 쪽 대응 | 하는 일 |
|---|---|---|
| Node.js | JVM | 내 컴퓨터에서 JS를 실행하는 환경. 개발 도구(Vite, Vitest)가 여기서 돈다. 완성된 앱은 폰 브라우저에서 돈다 |
| npm | Gradle / Maven | 라이브러리 설치, 명령 실행 |
| `package.json` | `build.gradle` / `pom.xml` | 의존성 목록과 실행 명령(`scripts`) |
| `package-lock.json` | `gradle.lockfile` | 설치된 정확한 버전 기록. Git에 올린다 |
| `node_modules/` | `~/.m2`, `~/.gradle/caches` | 설치된 라이브러리. 프로젝트 폴더마다 따로 생기고, Git에 올리지 않는다 |
| Vite | `bootRun` + `bootJar` | 개발 서버 실행(`npm run dev`), 배포용 파일 만들기(`npm run build`) |
| Vitest | JUnit 5 + AssertJ | 테스트 |
| `tsconfig.json` | `javac` 옵션 | TypeScript 컴파일러 설정 |

`package.json`의 `scripts`에 이름을 붙여 둔 명령을 `npm run 이름`으로 실행한다. `test`는 자주 쓰는 이름이라 `run` 없이 `npm test`로도 된다.

```json
"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "test": "vitest run",
  "test:watch": "vitest"
}
```

## 1. 순수 함수

**같은 입력을 넣으면 항상 같은 결과가 나오고, 바깥의 무언가(현재 시각, DB, 화면, 전역 변수)를 읽거나 바꾸지 않는 함수**다. `Math.max(a, b)` 같은 함수가 대표적이다.

`harvestCalc.ts`의 모든 함수가 순수 함수다.

```ts
export function getHouseStatus(
  records: readonly FarmRecord[], // 기록 목록 (readonly: 함수 안에서 배열을 못 바꾸게 함)
  houseNo: number,
  today: string,                  // ← "오늘"을 밖에서 받는다
): HouseStatus
```

### 왜 "오늘"을 인자로 받나

함수 안에서 현재 날짜를 직접 읽으면 **테스트를 돌리는 날마다 결과가 달라진다.** 그러면 "수확 가능일 당일부터 🟢" 같은 경계를 고정해서 검사할 수 없다. 오늘을 인자로 받으면 테스트에서 `'2026-10-21'`을 넣어 날짜를 고정할 수 있다. 화면에서는 진짜 오늘 날짜(한국 시간)를 구해서 넘겨 주면 된다.

**Spring 대응**: 서비스에서 `LocalDate.now()`를 직접 부르지 않고 `java.time.Clock`을 빈으로 주입받아, 테스트에서는 `Clock.fixed(...)`로 바꿔 끼우는 것과 목적이 같다. 여기서는 더 단순하게 날짜 값 자체를 넘긴다.

```java
// Spring에서 흔한 방식
@Service
class HarvestService {
  private final Clock clock;
  HarvestService(Clock clock) { this.clock = clock; }
  HouseStatus status(int houseNo) {
    LocalDate today = LocalDate.now(clock); // 테스트에서는 고정된 Clock
    ...
  }
}
```

### 순수 함수라서 좋은 점

- **테스트가 쉽고 빠르다.** DB도, 서버도, 브라우저도 필요 없다. 테스트 51개가 0.2초 안에 끝난다. Spring으로 치면 `@SpringBootTest` 없이 `new`로 객체를 만들어 바로 검사하는 순수 단위 테스트다
- **오프라인에서도 동작한다.** 서버에 묻지 않고 폰 안의 기록만으로 계산한다. 그래서 `CLAUDE.md`에서 이 계산을 서버나 DB 함수로 옮기지 말라고 정해 두었다

## 2. 날짜 계산

### JS의 `Date`가 불편한 점

- JS의 기본 `Date`는 **항상 시각(밀리초)까지 들고 있다.** Java의 `LocalDate`처럼 "날짜만" 담는 기본 타입이 없다
- 그리고 **폰의 시간대 설정을 따라간다.** 같은 코드가 한국 폰과 다른 시간대 폰에서 다른 날짜를 낼 수 있다
- 월이 **0부터 시작한다** (1월이 0). Java의 옛날 `Calendar`와 같은 함정이다

### 그래서 이렇게 했다

1. 날짜는 `"YYYY-MM-DD"` 문자열로만 저장한다 (`CLAUDE.md` 데이터 규칙)
2. 더하고 뺄 때만 "1970-01-01부터 며칠째"인 정수로 바꾼다. 시간대가 없는 UTC 기준으로만 계산한다
3. 계산이 끝나면 다시 문자열로 돌린다

```ts
function toDayNumber(date: string): number {
  const match = DATE_PATTERN.exec(date)            // 정규식으로 "2026-10-21" 형식 확인
  if (!match) throw new Error(`날짜 형식이 아닙니다: ${date}`)
  const [, y, m, d] = match                         // 구조 분해: match[1], [2], [3]을 꺼냄
  const dayNumber = Date.UTC(Number(y), Number(m) - 1, Number(d)) / MS_PER_DAY  // 월은 0부터라 -1
  if (fromDayNumber(dayNumber) !== date) throw new Error(`없는 날짜입니다: ${date}`)
  return dayNumber
}
```

- `` `...${date}` ``는 **템플릿 문자열**이다. Java의 `"..." + date`나 `String.format`과 같다 (백틱 `` ` ``으로 감싼다)
- `Date.UTC`는 `2026-02-30`처럼 없는 날짜를 넣으면 에러 없이 3월 2일로 넘겨 버린다. 그래서 다시 문자열로 돌려서 처음과 같은지 확인한다
- `===`, `!==`는 JS의 비교 연산자다. `==`도 있지만 타입을 멋대로 바꿔서 비교해서(`1 == '1'`이 true) 쓰지 않는다

**Spring 대응**: Java에서는 `LocalDate.parse("2026-10-21").plusDays(14)`, `ChronoUnit.DAYS.between(a, b)`로 끝나는 일이다. JS에 이런 기본 기능이 없어서 직접 만들었다.

### 문자열 비교가 곧 날짜 비교

`"YYYY-MM-DD"`는 자릿수가 고정이라 문자열 크기 비교가 날짜 순서와 같다. `"2026-10-09" < "2026-10-21"`은 true다. 그래서 `today >= readyDate`처럼 바로 비교한다. (Java에서는 `String`에 `<`를 못 쓰고 `compareTo`를 써야 하지만, JS는 문자열에도 `<`가 된다)

## 3. Vitest로 테스트 쓰기

### 파일 위치와 이름

- 테스트 파일은 **검사할 파일 바로 옆**에 `이름.test.ts`로 둔다 (`harvestCalc.ts` 옆에 `harvestCalc.test.ts`)
- Vitest가 `.test.ts`로 끝나는 파일을 알아서 찾아 돌린다
- Java는 `src/main/java`와 `src/test/java`로 폴더를 나누고 `*Test.java`를 찾는다. 규칙만 다르고 생각은 같다

### 기본 모양

```ts
import { describe, expect, it } from 'vitest'
import { getHouseStatus } from './harvestCalc'

describe('getHouseStatus', () => {                       // 테스트 묶음
  const today = '2026-10-21'

  it('수확 가능일 당일이면 🟢 수확 가능', () => {          // 테스트 하나
    const status = getHouseStatus([harvest('h', 1, '2026-09-16')], 1, today) // 09-16 + 35일 = 10-21
    expect(status.kind).toBe('ready')
    expect(status.daysSinceHarvest).toBe(35)
  })
})
```

- `import { ... } from '...'`는 Java의 `import`와 같다. 다른 파일에서 `export`한 것만 가져올 수 있다 (Java의 `public`과 비슷). `'./harvestCalc'`처럼 `./`로 시작하면 같은 폴더의 파일이다
- `describe`, `it`은 **함수를 인자로 받는 함수**다. `() => { ... }`가 그 인자로 넘기는 화살표 함수(Java 람다)다. 그래서 중괄호와 괄호가 `}, )`, `})`처럼 겹친다
- 테스트 이름을 한국어 문장으로 쓴다. 실패하면 이 문장이 그대로 표시된다

### Vitest와 JUnit 대응표

| Vitest | JUnit 5 / AssertJ |
|---|---|
| `describe('묶음', () => { ... })` | `@Nested` 클래스 + `@DisplayName("묶음")` |
| `it('설명', () => { ... })` | `@Test` + `@DisplayName("설명")` |
| `expect(a).toBe(b)` | `assertThat(a).isEqualTo(b)` — 숫자·문자열 같은 기본값 비교 (Java의 `==`에 가까움) |
| `expect(a).toEqual(b)` | `assertThat(a).usingRecursiveComparison().isEqualTo(b)` — 객체·배열의 **내용**을 비교 (Java의 `equals()`에 가까움) |
| `expect(a).toBeNull()` | `assertThat(a).isNull()` |
| `expect(() => f()).toThrow()` | `assertThatThrownBy(() -> f())` |

`toBe`와 `toEqual`의 차이가 중요하다. `{ kind: 'ready' }` 같은 객체 두 개는 내용이 같아도 다른 객체라 `toBe`로는 실패한다. 객체를 비교할 때는 `toEqual`을 쓴다.

### 테스트용 도우미 함수

기록 하나를 만들 때마다 필드를 전부 쓰면 길어서, 테스트 파일 위쪽에 도우미를 만들어 두었다.

```ts
const common = { memo: null, recorded_by: 'user-1', recorded_at: '2026-10-01T09:00:00+09:00' }

function harvest(id: string, house_no: number, work_date: string, cycle_days = 35): HarvestRecord {
  return { ...common, id, house_no, work_date, type: 'harvest', cycle_days }
}
```

- `...common`은 **전개 문법**이다. `common` 객체의 필드를 전부 복사해 넣는다
- `{ id, house_no }`는 `{ id: id, house_no: house_no }`의 줄임 표현이다
- `cycle_days = 35`는 **기본값이 있는 인자**다. `harvest('h', 1, '2026-10-01')`처럼 빼먹으면 35, `harvest('h', 1, '2026-10-01', 40)`처럼 넣으면 40이다. Java에는 없는 문법이라 메서드 오버로딩(`harvest(id, no, date)`가 `harvest(id, no, date, 35)`를 부르게)으로 흉내 낸다
- Java 테스트에서 쓰는 테스트 픽스처 팩토리 메서드나 빌더(`HarvestRecord.builder().cycleDays(40).build()`)와 같은 역할이다

### 무엇을 테스트했나 (`harvestCalc.test.ts` 49개)

- **날짜 계산**: 달과 해를 넘기는 날짜, 윤년 2월 29일, 형식이 틀리거나 없는 날짜
- **취소 처리**: 취소된 기록 빼기, 없는 id를 가리키는 취소 무시, 취소를 다시 취소하는 기록 무시
- **경계값**: 수확 가능일 당일(🟢), 하루 전(아직 아님), 오늘 수확·오늘 약(0일)
- **"마지막" 고르기**: 입력 순서와 상관없이 가장 늦은 기록, 같은 날이면 나중에 입력한 기록, 시간대 표기가 달라도 같은 순간으로 비교
- **결정 사항**: 수확 기록 없이 약 기록만 있으면 ⚪ 수확 기록 없음, 약을 쳐도 🟢 판단은 바뀌지 않음 ([[결정기록]])
- **수확 중**: 시작만 있으면 수확 중(당일 0일), 완료하면 끝남, 같은 날 시작·완료, 시작 없이 완료만, 시작 취소
- **문제**: 생김 / 해결됨 / 다시 생김, 배수·균사 따로 판단, 생김·해결됨 기록 취소, 다른 동은 보지 않음

규칙별로 어떤 테스트가 지키는지는 [[2026-10-22-1단계-코드-읽기]] 5번에 표로 있다.

경계값 테스트가 특히 중요하다. `>`와 `>=` 하나 차이로 🟢가 하루 늦게 뜬다.

## 4. 돌리는 법

- `npm test`: 한 번 돌리고 끝낸다. `Tests 51 passed`처럼 failed 없이 나오면 전부 통과
- `npm run test:watch`: 켜 두면 파일을 저장할 때마다 바뀐 부분과 관련된 테스트만 다시 돈다. 끌 때는 `q`. Spring 쪽에서는 `./gradlew test --continuous`가 비슷하다
- **테스트가 정말 검사하는지 확인하기**: 일부러 코드를 틀리게 바꿔 본다. 예를 들어 `harvestCalc.ts`의 `today >= readyDate`를 `today > readyDate`로 바꾸면 "수확 가능일 당일이면 🟢 수확 가능" 테스트가 실패해야 한다. 실패하지 않으면 그 테스트는 아무것도 지켜 주지 못하는 것이다. 확인한 뒤에는 꼭 되돌린다
- **내 상황 넣어 보기**: 테스트 파일에 `it(...)`을 하나 추가하고 `harvest()`, `spray()`, `cancel()` 도우미로 기록을 만든다. `console.log(status)`를 넣으면 계산 결과가 터미널에 찍힌다 (Java의 `System.out.println`)
