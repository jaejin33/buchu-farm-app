# JWT와 요청 인증

6-4(올리기)를 하다가 "지금 JWT를 쓰고 있나?"라는 질문에서 나온 내용이다. 답은 **쓰고 있다.** 다만 우리가 만든 것은 없고, Supabase Auth가 만들어 주고 `supabase-js`가 알아서 붙인다. 로그인 표(access token / refresh token)의 수명과 오프라인 이야기는 [[2026-10-23-환경-변수와-Supabase-권한]] 4번, 이 프로젝트의 코드는 [[2026-10-23-6단계-코드-읽기]].

## 1. JWT란

JWT(JSON Web Token)는 **"이 사람은 누구이고 언제까지 유효하다"를 적고 서버가 서명한 글자 한 줄**이다. 점(`.`) 두 개로 세 부분이 나뉜다.

```
eyJhbGciOi...  .  eyJzdWIiOiIxMjM0...  .  SflKxwRJSMeKKF2QT4f...
   머리              내용(payload)             서명
```

| 부분 | 들어 있는 것 | 예 |
|---|---|---|
| 머리 | 서명 방식 | `{"alg": "...", "typ": "JWT"}` |
| 내용 | 사용자 정보와 유효 기간 | `{"sub": "사용자 id", "role": "authenticated", "exp": 1792745000, ...}` |
| 서명 | 머리 + 내용을 서버만 아는 키로 서명한 값 | 사람이 읽을 수 없음 |

- 머리와 내용은 **암호화가 아니라 글자 바꾸기(base64url)일 뿐**이다. 누구나 풀어서 읽을 수 있다. 그래서 비밀번호 같은 것은 넣지 않는다
- 서명이 있어서 **고칠 수는 없다.** 내용의 `sub`를 다른 사람 id로 바꾸면 서명이 안 맞아 서버가 거절한다
- 서버는 서명만 확인하면 되고, 세션 표를 따로 들고 있지 않아도 된다

우리 앱의 JWT 내용에서 중요한 항목은 세 개다.

| 항목 | 뜻 | 우리 앱에서 |
|---|---|---|
| `sub` | 누구 (subject) | Supabase Auth 사용자 id. 기록의 `recorded_by`에 넣는 값과 같다 |
| `role` | 역할 | `authenticated` (로그인함). GRANT가 이 역할을 본다 |
| `exp` | 언제까지 유효 | 발급 후 1시간. 1970년 1월 1일부터 센 초 |

## 2. 우리 앱에서 요청 하나가 지나가는 길

6-4에서 기록 하나를 올릴 때 일어나는 일이다.

```
1. 로그인 (처음 한 번)
   signInWithPassword → Supabase Auth가 access token(JWT, 1시간) + refresh token을 준다
   → supabase-js가 localStorage의 sb-<프로젝트 id>-auth-token에 넣는다 (persistSession: true)

2. 올리기 (syncService.ts)
   getSession()  → JWT가 지났으면 refresh token으로 새 JWT를 받는다 (인터넷 필요)
   insert(...)   → supabase-js가 요청에 헤더 두 개를 붙인다
                    apikey: sb_publishable_...        ← 어느 프로젝트인지
                    Authorization: Bearer eyJhbGci... ← 누구인지 (JWT)

3. Supabase 서버
   JWT 서명 확인 → role = authenticated → GRANT 검사 (insert 해도 되나)
   → sub를 auth.uid()로 꺼냄 → RLS 검사: recorded_by = auth.uid() ?
   → 맞으면 저장, 아니면 "new row violates row-level security policy"
```

**`apikey`와 `Authorization`은 하는 일이 다르다.** 처음 볼 때 가장 헷갈리는 부분이다.

| 헤더 | 값 | 하는 일 | 공개되어도 되나 |
|---|---|---|---|
| `apikey` | publishable 키 | "우리 Supabase 프로젝트로 온 요청이다" | 된다 (앱 JS 파일에 들어 있음) |
| `Authorization: Bearer` | JWT | "이 요청은 아버지가 보냈다" | **안 된다.** 비밀번호처럼 다룬다 |

로그인 전에는 `Authorization` 자리에 publishable 키가 들어가고, 서버는 `anon`(로그인 안 함)으로 본다. 그래서 GRANT에서 막힌다 → [[2026-10-23-환경-변수와-Supabase-권한]] 3번.

**앱이 따로 적어 두는 `buchu-farm:user`는 JWT가 아니다.** 인터넷이 끊겨도 로그인 화면이 뜨지 않게 "누가 로그인했나"만 적은 메모다. 서명이 없어서 서버는 이 값을 믿지 않고, 서버로 보내지도 않는다. 서버가 믿는 것은 JWT뿐이다.

## 3. Spring에서는

Spring Security의 **JWT 리소스 서버**와 같은 구조다. 다른 점은 검사하는 쪽이 우리 서버가 아니라 Supabase(DB 앞의 창구)라는 것이다.

```java
// Spring: 요청의 Bearer 토큰을 확인하고, 그 안의 사용자 id로 권한을 검사한다
@Configuration
class SecurityConfig {
  @Bean
  SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())   // ≈ GRANT ... to authenticated
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));  // ≈ Supabase가 JWT 서명 확인
    return http.build();
  }
}

@PostMapping("/records")
void add(@RequestBody FarmRecord r, @AuthenticationPrincipal Jwt jwt) {
  if (!r.recordedBy().equals(jwt.getSubject()))                       // ≈ RLS: recorded_by = auth.uid()
    throw new AccessDeniedException("자기 이름으로만 추가");
  repository.save(r);
}
```

| Spring | Supabase (우리 앱) |
|---|---|
| `oauth2ResourceServer().jwt()` | Supabase가 모든 요청의 JWT 서명을 확인 |
| `jwt.getSubject()` | `auth.uid()` |
| `.authenticated()` | `grant ... to authenticated` |
| 컨트롤러·서비스의 `if` 검사 | RLS 정책 (`with check (...)`) |
| 토큰을 만드는 인증 서버 (Keycloak 등) | Supabase Auth |
| 프론트가 `Authorization` 헤더를 직접 붙임 | `supabase-js`가 알아서 붙임 |

Spring의 **세션 로그인**(`JSESSIONID` 쿠키)과는 다르다. 세션 방식은 서버가 "이 세션 = 아버지"라는 표를 메모리나 DB에 들고 있다. JWT는 서버가 아무것도 들고 있지 않고, 요청에 딸려 온 JWT의 서명만 확인한다.

## 4. 직접 열어 보기

`npm run dev`로 연 앱(로그인한 상태)에서 F12를 누른다.

- **Application → Local Storage → `http://localhost:5173`** 를 연다
  - `sb-tjzvwmddricxyihcbkzb-auth-token`: supabase-js가 넣은 것이다. 안에 `access_token`(JWT), `refresh_token`, `expires_at`이 있다
  - `buchu-farm:user`: 우리 앱이 적은 메모다
- JWT의 내용(가운데 부분)은 Console에서 풀어 볼 수 있다

```js
JSON.parse(atob(JSON.parse(localStorage['sb-tjzvwmddricxyihcbkzb-auth-token']).access_token.split('.')[1]))
```

안쪽부터 읽는다.

| 조각 | 하는 일 | Java로 치면 |
|---|---|---|
| `localStorage['키']` | localStorage에서 글자를 꺼낸다. `localStorage.getItem('키')`와 같다 | `map.get("키")` |
| `JSON.parse(...)` | JSON 글자 → 객체 | Jackson `readValue` |
| `.access_token` | 객체에서 그 항목 | `obj.getAccessToken()` |
| `.split('.')` | 점으로 잘라 배열로. JWT는 세 조각이 된다 | `token.split("\\.")` |
| `[1]` | 둘째 조각(내용). 배열은 0부터 센다 | `parts[1]` |
| `atob(...)` | base64 글자를 원래 글자로 | `Base64.getDecoder().decode(...)` |
| 바깥 `JSON.parse(...)` | 풀린 글자(JSON) → 객체 | `readValue` |

결과로 `sub`, `role`, `exp`, `email` 등이 보인다. `exp`를 사람이 읽는 시각으로 보려면 `new Date(exp * 1000)`을 쓴다. JS의 시각은 초가 아니라 밀리초라서 1000을 곱한다.

**조심할 것:** 토큰을 jwt.io 같은 외부 사이트에 붙여 넣지 않는다. 1시간 안에는 그 토큰으로 우리 기록을 보고 넣을 수 있다. refresh token은 더 오래 쓸 수 있어서 더 조심한다.
