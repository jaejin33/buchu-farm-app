# PWA와 서비스 워커

5.1단계에서 앱을 홈 화면에 추가할 수 있게 하고, 인터넷이 끊겨도 열리게 했다. 그때 나온 내용을 정리한다. 이 프로젝트의 설정 파일은 [[2026-10-23-5단계-코드-읽기]].

## 1. PWA = 웹사이트 + 두 가지 파일

PWA(Progressive Web App)는 새 기술 하나가 아니라, 보통 웹사이트에 **파일 두 개를 더한 것**이다.

| 파일 | 하는 일 | 없으면 |
|---|---|---|
| **앱 소개 파일** (`manifest.webmanifest`) | 앱 이름, 아이콘, 바탕색, "주소창 없이 열기"를 적는다 | 홈 화면에 추가해도 그냥 즐겨찾기처럼 보인다 |
| **서비스 워커** (`sw.js`) | 앱 파일을 폰에 받아 두고, 인터넷이 없으면 받아 둔 파일로 연다 | 인터넷이 끊기면 "연결 없음" 화면이 뜬다 |

폰은 앱 소개 파일을 보고 홈 화면 아이콘을 만든다. 아이콘을 눌러 열면 주소창이 없어서 앱처럼 보인다(`display: standalone`).

Spring 쪽에는 대응하는 것이 없다. 둘 다 브라우저가 읽는 파일이다. 안드로이드 앱의 `AndroidManifest.xml`이 앱 이름·아이콘을 적는 것과 비슷한 역할이다.

## 2. 서비스 워커: 브라우저 안의 작은 대리인

서비스 워커는 페이지와 인터넷 사이에 서 있는 JS 파일이다. 페이지가 파일을 달라고 하면 서비스 워커가 먼저 받아서, 폰에 받아 둔 것이 있으면 그걸 준다.

```
처음 열 때 (인터넷 됨)
  페이지 ──요청──→ 서비스 워커 ──→ Vercel
                     └ 앱 파일 12개를 폰 저장소(캐시)에 받아 둠

다음에 열 때 (인터넷 끊김)
  페이지 ──요청──→ 서비스 워커 ──→ (인터넷 없음)
                     └ 받아 둔 파일로 대답 → 앱이 열림
```

- **미리 받아 두기(precache):** 빌드할 때 `vite-plugin-pwa`가 `dist/`의 파일 목록(HTML, CSS, JS, 아이콘)을 서비스 워커 안에 적어 둔다. 처음 열 때 이 목록을 모두 받는다
- **페이지는 서비스 워커가 있든 없든 똑같이 짠다.** 우리 화면 코드는 서비스 워커를 모른다. 그래서 `npm run dev`에서는 서비스 워커를 끄고(플러그인 기본값) 개발한다
- **기록 저장과는 관계없다.** 기록은 IndexedDB에 있다([[2026-10-22-IndexedDB와-Dexie]]). 서비스 워커는 **앱 파일**만 받아 둔다. 둘이 합쳐져야 "인터넷 없이 열리고, 인터넷 없이 기록한다"가 된다
- `https://` 주소나 `localhost`에서만 켜진다 → [[2026-10-23-https와-Vercel-자동-배포]] 1번

Spring으로 굳이 빗대면 브라우저 안에 들어간 `Filter`나 리버스 프록시(Nginx)와 비슷하다. 요청을 가로채서 직접 대답하거나 뒤로 넘긴다. 다른 점은 **사용자 폰 안에서** 돈다는 것이다.

## 3. 새 버전은 어떻게 들어오나

push하면 Vercel에 새 파일이 올라가지만, 폰은 받아 둔 옛 파일로 앱을 연다. 그래서 새 버전이 들어오는 순서가 있다.

```
1번째 열기: 옛 버전이 뜸 ─┐ (그 사이 서비스 워커가 새 sw.js를 확인 → 새 파일을 받아 둠)
2번째 열기: 새 버전이 뜸 ←┘
```

`registerType: 'autoUpdate'`는 "새 버전을 받으면 묻지 않고 바꿔 끼운다"는 뜻이다. 다만 우리는 **화면을 저절로 새로 고치지 않게** 했다(플러그인의 화면 코드 `virtual:pwa-register`를 쓰지 않음). 아버지가 기록을 입력하는 중에 화면이 바뀌면 입력하던 것이 날아가기 때문이다 → [[결정기록]] "PWA: 새 버전은 다음에 열 때 뜬다"

그래서 **push한 뒤 고친 화면을 보려면 앱을 두 번 열어야 한다.** 고쳤는데 그대로라면 먼저 이걸 의심한다.

**push한 지 며칠이 지나도 똑같다** (2026-10-26 질문 "push한 지 좀 됐어도 두 번 열어야 해?"). 폰은 앱이 닫혀 있는 동안 새 버전을 확인하지 않는다. 확인은 앱을 열 때만 하고, 그 열기에는 이미 받아 둔 옛 파일이 먼저 뜬다. 열 때 서버에 먼저 묻고 기다리면, 하우스 안에서 인터넷이 끊겼을 때 앱이 안 열리기 때문이다.

- "두 번"은 **push 뒤에** 센 횟수다. push 뒤 두 번 열었으면 그 폰은 이미 새 버전이고, 그다음부터는 한 번에 뜬다
- 1번째 열기 때 인터넷이 끊겨 있었으면 새 파일을 못 받았으니 세 번, 네 번 걸릴 수 있다

Spring으로 치면 비슷한 것이 없다. 서버는 배포하면 다음 요청부터 바로 새 코드다. 굳이 대응시키면 브라우저가 들고 있는 정적 파일 캐시가 "다음 요청 때 새것인지 확인"하는 것과 비슷한데, 서비스 워커는 확인하는 동안에도 옛것을 먼저 보여 준다는 점이 다르다.

### 설치한 사람들 폰에서는

앱스토어 없이 **저절로 업데이트된다.** 다만 알아둘 것이 있다.

- **"열기"는 완전히 닫았다가 여는 것이다.** 폰은 뒤로 보내 둔 앱을 다시 띄울 때 새로 열지 않는다. 앱을 닫지 않고 계속 쓰면 며칠씩 옛 버전일 수 있다(특히 아이폰). 급한 수정이면 "앱을 한 번 닫았다 다시 열어 주세요"라고 말씀드린다
- **인터넷이 끊겨 있으면 새 버전을 못 받는다.** 옛 버전이 그대로 돌다가 인터넷이 될 때 받는다. 옛 버전도 정상 동작한다
- **기록과 로그인은 그대로다.** 바뀌는 것은 앱 파일(화면 코드)뿐이다. IndexedDB와 localStorage는 그대로 남는다
  - 그래서 **IndexedDB 구조를 바꿀 때는 옛 기록을 옮기는 코드를 같이 넣는다** (Dexie의 `db.version(2)`). Spring에서 컬럼을 바꿀 때 Flyway 마이그레이션을 같이 넣는 것과 같다
- **고장 난 코드도 똑같이 퍼진다.** push 전에 `npm test`, `npm run build`. 빌드가 실패하면 Vercel이 배포하지 않아 안전하고, 빌드는 됐는데 화면이 이상하면 다시 고쳐 push하거나 Vercel 화면에서 예전 배포로 되돌린다(Deployments → 예전 배포 → Instant Rollback / Promote to Production)
- 다시 띄울 때마다 새 버전을 확인하게 할 수도 있다(화면이 다시 보일 때 `registration.update()`). 지금은 넣지 않았다. "고쳤다는데 그대로"인 일이 자주 생기면 그때 넣는다
- 한 번 열면 바뀌게 할 수도 있다: 새 버전을 받아 둔 상태에서 **하우스 목록 화면에 있을 때만**(입력 중이 아닐 때) 저절로 새로 고친다. 2026-10-26 Claude가 말했고 정하지 않았다

## 4. 갤럭시와 아이폰

| | 갤럭시 (크롬) | 아이폰 (사파리) |
|---|---|---|
| 설치 | ⋮ 메뉴 → "홈 화면에 추가" → "설치". 크롬이 "앱 설치"를 먼저 띄워 주기도 함 | 공유 버튼 → "홈 화면에 추가". 안내가 저절로 뜨지 않음 |
| 아이콘 | manifest의 아이콘 (`maskable`은 기종마다 동그라미 등으로 잘라 씀) | `index.html`의 `apple-touch-icon` (manifest 아이콘은 안 씀) |
| 주소창 없이 열기 | manifest의 `display: standalone` | 같음 (iOS 16.4부터) |
| 받아 둔 기록 | 크롬에서 연 것과 설치한 앱이 같은 기록을 본다 | 사파리에서 연 것과 홈 화면 앱의 기록이 따로라고 알려져 있다 (확인 필요) |

- 카카오톡에서 링크를 누르면 카톡 안의 브라우저로 열려 설치가 안 된다. "다른 브라우저로 열기"로 크롬·사파리에서 연다
- 두 폰 모두 지원해야 한다 → [[결정기록]] "아버지 폰(갤럭시)과 형 폰(아이폰) 모두 지원"

## 5. 확인하는 법

**PC 크롬:**
1. `npm run build` → `npm run preview` (배포와 같은 파일. `npm run dev`는 서비스 워커가 꺼져 있다)
2. F12 → **Application** 탭 → 왼쪽 **Service workers**: `sw.js`가 "activated"인지 본다. **Manifest**: 이름·아이콘이 보이는지 본다
3. Service workers의 **Offline**에 체크하고 새로 고침 → 앱이 뜨면 된다

**`npm run preview`에도 서비스 워커가 켜져 있다.** 그래서 PC에서도 "두 번 열어야 새 버전" 규칙이 그대로다. 코드를 고치고 다시 빌드해도 F5를 한 번 누르면 옛 화면이 뜬다 (10월 26일 8단계 확인 때 겪음). 고친 화면을 볼 때는 `npm run dev`를 쓴다 → [[2026-10-22-Vite-개발-서버와-화면-확인]] 5번

**진짜 폰:** Vercel 주소로 설치 → 비행기 모드 → 앱을 완전히 닫았다 다시 열기 → 목록과 기록이 그대로면 된다.

## 6. 새 버전이 퍼지는 동안: 옛 버전이 새 기록을 받을 때

새 버전은 폰마다 받는 때가 다르다 (3번). 그래서 **잠깐 동안 옛 버전 폰과 새 버전 폰이 같은 서버 기록을 함께 본다.** 새 버전이 새 모양의 기록을 올리면, 옛 버전도 내려받기로 그 기록을 받는다. 이때 옛 코드가 처음 보는 모양을 어떻게 다루느냐에 따라 결과가 갈린다.

| 단계 | 새 모양 | 옛 버전이 받으면 |
|---|---|---|
| 7단계 | 새 칸 `fertilizer` (비료 이름) | 모르는 칸이라 버린다. 앱은 멀쩡하지만 그 폰에서는 이름이 안 보인다 (아래 "버린 칸은 다시 안 온다") |
| 8단계 | 기존 칸 `problem`에 새 값 `'other'` | 이력 화면이 `PROBLEM_TAG['other'].icon`을 읽다가 에러 → **하얀 화면** |
| 9단계 | 새 칸 `amount_ml`·`bags` (약·관비 ml, 비료 포 수) | 7단계와 같다. 이번에는 새 버전이 다시 받아 채운다 |

**모르는 칸**은 무시하면 그만이지만, **아는 칸의 모르는 값**은 옛 코드가 "이 값들뿐"이라고 믿고 짠 곳에서 터진다.

### 버린 칸은 다시 안 온다 (9단계에 고침)

"버린다"는 말은, 옛 버전이 서버에서 받은 한 줄을 폰에 저장할 때 **자기가 아는 칸만 골라 담는다**는 뜻이다 (`syncService.ts`의 `fromRow`, [[2026-10-23-6단계-코드-읽기]] 9번).

```
서버에서 온 줄:   { type: 'spray', pesticide: '가약', amount_ml: 20, ... }
옛 버전이 저장:   { type: 'spray', pesticide: '가약', ... }        ← 20이 빠짐
```

```java
// Spring으로 치면: 옛 DTO에 amountMl 필드가 없다
class SprayDto { String pesticide; }     // Jackson은 모르는 amount_ml을 무시하고 객체를 만든다
repository.save(toEntity(dto));          // 저장된 행에는 ml가 없다
```

문제는 그다음이다. 내려받기는 원래 "폰에 없는 id만 추가"였다. 옛 버전 때 ml 없이 저장한 기록은 이미 폰에 있으니, 새 버전이 된 뒤에도 다시 받지 않는다. 그래서 **그 폰에서는 그 기록의 ml가 계속 비어 보인다.** 서버(원본)에는 남아 있어서 기록이 사라지지는 않는다.

예: 형 폰이 먼저 새 버전이 되어 "3동 약 가약 20ml"를 저장한다 → 아버지 폰(옛 버전)은 "3동 약 가약"만 저장한다 → 다음 날 아버지 폰이 새 버전이 되어도 3동 약 기록은 다시 안 받는다.

9단계에서 두 가지를 바꿨다 → [[결정기록]] "내려받을 때 폰에 있는 보낸 기록은 서버 것으로 바꾼다"

1. 내려받을 때 폰에 있는 **보낸 기록**(`synced = 1`)은 서버 것으로 바꾼다. 서버 기록은 고쳐지지 않으니(추가만 함) 내용은 같고, 빠진 칸만 채워진다. **안 보낸 기록**(`synced = 0`)은 그대로 둔다 (아직 서버에 없거나, 올리기가 곧 1로 바꿀 것이라서)
2. "마지막으로 받은 시각"을 적어 두는 이름에 숫자를 붙였다 (`buchu-farm:last-received-at:2`). 새 버전은 이 이름으로 적힌 값을 못 찾으니 "처음 받는 폰"처럼 서버 기록을 처음부터 받는다 → 1번 덕에 빠진 칸이 채워진다. **기록에 칸을 또 더하면 이 숫자를 올린다** (`CLAUDE.md` 동기화 규칙)

다른 방법도 있었다: 읽는 버전을 먼저 퍼뜨리고 쓰는 버전을 나중에 push(아래), 또는 그냥 두고 "앱을 두 번 열어 주세요"라고 말씀드리기. 둘 다 사람이 지켜야 하거나 기다려야 해서 고르지 않았다.

Spring으로 치면 서버 여러 대를 하나씩 바꾸는 배포(롤링 배포) 중에, 새 서버가 enum에 새 값을 넣어 DB에 쓰고 옛 서버가 그 행을 읽는 것과 같다.

```java
enum HouseProblem { DRAINAGE, MYCELIUM }   // 옛 서버의 enum
HouseProblem.valueOf("OTHER");             // IllegalArgumentException (Jackson이면 InvalidFormatException)
```

해결 방법도 같다. **읽는 쪽을 먼저 바꾸고, 쓰는 건 나중에 한다.** 새 값을 읽을 줄 아는 버전을 먼저 모두에게 퍼뜨린 뒤에 새 값을 쓰기 시작한다.

- 이 앱에서는 push한 뒤 **모든 폰이 앱을 두 번 열어 새 버전을 받은 다음에** 직접 적은 문제를 저장한다 → [[결정기록]] "직접 적은 문제는 모든 폰이 새 버전을 받은 뒤에 저장한다"
- 시험 기록은 오프라인에서 저장하고 **취소까지 한 뒤** 온라인으로 돌린다. 취소된 기록은 옛 버전도 이력에 그리지 않아서 터지지 않는다
- 다음에 비슷한 일을 할 때는 "새 값을 읽을 줄 아는 버전"을 먼저 push하고, "새 값을 쓰는 버전"을 나중에 push하는 방법도 있다. 두 번 나눠 배포하는 것이다 (8단계는 한 번에 했다)

코드는 [[2026-10-22-3단계-코드-읽기]] 14번 "옛 버전 앱이 새 기록을 받으면".
