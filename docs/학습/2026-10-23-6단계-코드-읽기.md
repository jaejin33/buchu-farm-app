# 6단계 코드 읽기: Supabase 로그인과 올리기·내려받기 (6-1 ~ 6-5)

6단계는 작게 나눠 진행한다. 이 노트는 지금까지 한 6-1(Supabase 프로젝트, 환경 변수), 6-2(테이블과 권한), 6-3(로그인 화면), 6-4(올리기), 6-5(내려받기)를 다룬다. 6-6은 진행하면서 덧붙인다. 개념은 [[2026-10-23-환경-변수와-Supabase-권한]], [[2026-10-23-JWT와-요청-인증]], [[2026-10-23-시크릿-창으로-두-폰-시험하기]].

## 1. 파일 지도

```
.env.example            ← .env 견본 (Git에 올림)
.env                    ← 진짜 값 (Git에 안 올림)
supabase/records.sql    ← Supabase SQL Editor에서 실행한 것 (테이블 + GRANT + RLS)

src/
├ App.tsx               ─ 로그인 전이면 Login, 아니면 예전처럼 목록·입력·이력. 로그인돼 있으면 startSync()
├ pages/Login.tsx       ─ signIn() 부름
├ data/auth.ts          ─ 로그인, getCurrentUser()  ── getSupabase() 부름
├ data/supabase.ts      ─ Supabase 클라이언트 (@supabase/supabase-js는 여기서만 import)
├ data/recordRepository.ts ─ addRecord()가 getCurrentUser()로 입력한 사람을 채우고, 저장 뒤 uploadPending()
└ data/syncService.ts   ─ uploadPending(): 안 보낸 기록을 Supabase로, downloadNew(): 새로 들어온 기록을 폰으로,
                          startSync(): 앱 열 때·재연결 때·화면으로 돌아올 때 둘 다  ── db, getSupabase() 부름
```

화살표 방향: **화면 → data → Supabase.** 화면은 Supabase를 모른다(`CLAUDE.md` 아키텍처). `App.tsx`는 `startSync()`만 부르고, 무엇을 어디로 보내고 받는지는 모른다. 내려받은 기록도 IndexedDB에 들어갈 뿐이라, 화면은 6-5 전과 똑같이 IndexedDB만 보고 그린다.

언제 올리고 받는지는 10번 표에 모았다.

## 2. `supabase/records.sql`

`CLAUDE.md`의 `records` 테이블에 권한 두 겹을 더한 것이다. 줄마다 뜻은 [[2026-10-23-환경-변수와-Supabase-권한]] 3번.

- 레포에 남겨 둔 이유: Supabase 화면에서 실행한 것은 코드에 안 남는다. 나중에 프로젝트를 다시 만들거나 서버를 바꿀 때 무엇을 했는지 알 수 있게 한다. Spring의 Flyway 마이그레이션 파일(`V1__create_records.sql`)과 같은 역할이다. 다만 자동으로 실행되지 않는다
- `received_at`에 `not null`과 색인을 더했다. 색인은 6-5(내려받기)의 "마지막으로 받은 시각 이후" 찾기를 빠르게 한다

## 3. `data/supabase.ts`: 처음 쓸 때 만든다

```ts
let client: SupabaseClient | null = null

export function getSupabase(): SupabaseClient {
  if (client !== null) return client
  const url = import.meta.env.VITE_SUPABASE_URL
  const key = import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY
  if (!url || !key) throw new Error('.env에 ... 없어요')
  client = createClient(url, key, { auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: false } })
  return client
}
```

- **처음 부를 때 한 번 만들고, 그다음부터는 같은 것을 돌려준다.** Java의 지연 초기화 싱글턴과 같다
  ```java
  private static SupabaseClient client;
  public static SupabaseClient get() { if (client == null) client = create(...); return client; }
  ```
  Spring이라면 `@Bean`으로 두면 되는 일이다. 우리는 DI 컨테이너가 없어서 직접 한다
- 파일을 불러오자마자 만들지 않는 이유: 테스트에는 `.env` 값이 없다. 불러오자마자 만들면 `addRecord`를 테스트할 때도(auth.ts → supabase.ts로 이어져서) 에러가 난다
- `let`: 다시 넣을 수 있는 변수. `const`는 다시 못 넣는다. Java의 일반 변수와 `final`
- `!url`: 값이 `undefined`이거나 빈 글자(`''`)면 `true`다. JS는 `undefined`, `null`, `''`, `0`을 "없는 것"(falsy)으로 본다
- `persistSession`: 로그인 표를 폰에 남긴다. `autoRefreshToken`: 표가 지나기 전에 인터넷으로 새로 받는다. `detectSessionInUrl: false`: 메일 링크·카카오 로그인을 안 쓰니 주소창을 뒤지지 않는다

## 4. `data/auth.ts`: 로그인과 "지금 누구"

```ts
export function getCurrentUser(): CurrentUser | null {
  try {
    const saved = localStorage.getItem(CURRENT_USER_KEY)
    return saved === null ? null : (JSON.parse(saved) as CurrentUser)
  } catch {
    return null
  }
}

export type SignInResult = 'ok' | 'wrong' | 'offline' | 'failed'

export async function signIn(email: string, password: string): Promise<SignInResult> {
  if (!navigator.onLine) return 'offline'
  const { data, error } = await getSupabase().auth.signInWithPassword({ email: email.trim(), password })
  if (error) {
    if (isAuthRetryableFetchError(error)) return 'offline'
    if (error.code === 'invalid_credentials') return 'wrong'
    return 'failed'
  }
  const user: CurrentUser = { id: data.user.id, email: data.user.email ?? email.trim() }
  localStorage.setItem(CURRENT_USER_KEY, JSON.stringify(user))
  return 'ok'
}
```

- **"지금 누구"를 Supabase와 따로 적어 두는 이유:** 인터넷이 끊긴 채 앱을 열어도 로그인 화면이 뜨지 않게 하려는 것이다 → [[2026-10-23-환경-변수와-Supabase-권한]] 4번
- `try { ... } catch { return null }`: 저장된 글자가 깨졌거나 localStorage를 못 쓰는 환경이면 "로그인 안 됨"으로 본다. Java와 같지만 `catch` 뒤에 예외 변수를 안 적어도 된다
- `JSON.parse(saved) as CurrentUser`: `as`는 "이건 CurrentUser라고 믿어라"는 표시다. 실제로 검사하지는 않는다. Java의 캐스팅 `(CurrentUser) obj`와 비슷하지만, Java와 달리 틀려도 그 자리에서 에러가 나지 않는다
- **`SignInResult`: 글자 몇 개 중 하나인 타입.** Java의 `enum SignInResult { OK, WRONG, OFFLINE, FAILED }`처럼 쓴다. 화면은 이 값을 보고 안내 글을 고른다. Supabase 에러 모양을 화면이 몰라도 된다
- `const { data, error } = await ...`: 돌아온 객체에서 `data`와 `error`를 꺼내 각각 변수로 만든다(구조 분해). Supabase는 실패해도 예외를 던지지 않고 `error`에 담아 돌려준다. Java로 치면 `Result<T, E>`를 돌려받는 방식이다
- `isAuthRetryableFetchError`: "인터넷 문제라 다시 하면 될 수도 있는 에러"인지 본다. `invalid_credentials`는 이메일·비밀번호가 틀린 것이다
- `a ?? b`: `a`가 `null`이나 `undefined`면 `b`. Java의 `Objects.requireNonNullElse(a, b)`
- `navigator.onLine`: 브라우저가 아는 인터넷 연결 여부. 인터넷이 없는 게 확실하면 Supabase를 부르지도 않는다

## 5. `data/recordRepository.ts`: 입력한 사람

```ts
export async function addRecord(input: NewRecord): Promise<FarmRecord> {
  const user = getCurrentUser()
  if (user === null) throw new Error('로그인 전에는 기록할 수 없어요')
  const record: FarmRecord = { ...input, id: newId(), recorded_by: user.id, recorded_at: nowTimestamp() }
  await db.records.add({ ...record, synced: 0 })
  void uploadPending()
  return record
}

export async function removeTestRecords(): Promise<void> {
  await db.records.filter((r) => r.recorded_by === LOCAL_USER_ID).delete()
}
```

- `recorded_by`가 임시 id(`LOCAL_USER_ID`)에서 **로그인한 사람의 id**로 바뀌었다. 6-2의 RLS가 "자기 이름으로만 추가"를 검사하므로, 이 값이 로그인한 사람과 같아야 서버가 받는다
- 로그인 화면을 지나야 목록이 열리므로 `user === null`일 일은 없다. 그래도 혹시 모를 때 임시 id로 저장되지 않게 막는다
- **저장한 뒤 바로 올리기를 시작하지만 기다리지 않는다(6-4).** 폰에 저장(`await db.records.add`)이 끝나면 `addRecord`는 바로 끝나고, 화면은 목록으로 돌아가 "3동 약 저장했어요"를 띄운다. 올리기는 그 뒤에서 따로 돈다. `void`의 뜻은 8번
- **`removeTestRecords`: 로그인 직후 시험 기록을 지운다.** 기록은 추가만 한다는 규칙의 예외다 → [[결정기록]] "로그인할 때 시험 기록은 지운다"
  - `filter(...)`: 색인이 없는 항목(`recorded_by`)으로 고를 때 쓴다. 모든 기록을 하나씩 본다. 한 번만 부르고 기록도 적어서 괜찮다. 색인으로 찾는 `where('synced').equals(0)`와 다르다 → [[2026-10-22-IndexedDB와-Dexie]]
  - `.delete()`: 고른 것을 지운다. JPA의 `deleteAll(repository.findAll().stream().filter(...))`처럼

## 6. `pages/Login.tsx`

```tsx
const ERROR_TEXT: Record<Exclude<SignInResult, 'ok'>, string> = {
  wrong: '이메일이나 비밀번호가 맞지 않아요',
  offline: '인터넷이 되는 곳에서 로그인해 주세요',
  failed: '로그인하지 못했어요. 잠시 뒤 다시 눌러 주세요',
}

async function handleSubmit(e: FormEvent) {
  e.preventDefault()
  setBusy(true)
  setError(null)
  const result = await signIn(email, password)
  if (result === 'ok') { onLoggedIn(); return }
  setError(ERROR_TEXT[result])
  setBusy(false)
}
```

- **`Record<Exclude<SignInResult, 'ok'>, string>`:** "ok를 뺀 결과 셋마다 글자 하나"인 표다. 하나라도 빠뜨리면 TypeScript가 알려 준다. Java의 `EnumMap<SignInResult, String>`과 비슷한데, 빠진 칸을 컴파일러가 잡아 준다는 점이 다르다
  - 여기 `Record`는 TypeScript에 내장된 타입이다. 우리 기록 타입을 `FarmRecord`로 이름 지은 이유가 이것과 겹치지 않게 하려는 것이다 (`domain/types.ts` 주석)
  - `Exclude<A, B>`: A에서 B를 뺀 타입. `Exclude<'ok' | 'wrong' | 'offline' | 'failed', 'ok'>` = `'wrong' | 'offline' | 'failed'`
- `e.preventDefault()`: `<form>`을 제출하면 브라우저가 페이지를 새로 여는 것이 기본이다. 그걸 막고 우리가 처리한다
- `busy`: 로그인 중에는 버튼을 꺼서 두 번 누르지 않게 한다. 칸이 비어 있어도 버튼이 꺼진다
- 입력 칸 속성
  - `type="email"`, `inputMode="email"`: 폰이 @가 있는 키보드를 띄운다
  - `autoCapitalize="none"`: 폰이 첫 글자를 대문자로 바꾸지 않게 (이메일이 틀리는 흔한 이유)
  - `autoComplete="username"` / `"current-password"`: 폰이 저장해 둔 비밀번호를 채워 줄 수 있게
- 모양은 기록 입력 화면의 `.form-card`, `.text-input`, `.save`를 같이 쓴다(`import './RecordForm.css'`). 그래서 글자 20px, 버튼 높이가 다른 화면과 같다
- 가입 화면은 없다. 계정은 개발자가 Supabase 화면에서 만든다

## 7. `App.tsx`: 로그인 전이면 로그인 화면

```tsx
const [user, setUser] = useState(getCurrentUser)

// 로그인되어 있으면 주고받기 시작 (앱 열 때 한 번 + 인터넷 재연결·화면으로 돌아올 때마다)
useEffect(() => {
  if (user === null) return
  return startSync()
}, [user])

async function handleLoggedIn() {
  await removeTestRecords()
  setUser(getCurrentUser())
}

if (user === null) return <Login onLoggedIn={handleLoggedIn} />
if (records === undefined) return null
```

- `useState(getCurrentUser)`: 함수를 **부르지 않고 넘기면**(괄호 없음) React가 처음 한 번만 불러 처음 값으로 쓴다. `useState(getCurrentUser())`라고 쓰면 화면을 다시 그릴 때마다 localStorage를 읽는다
- `if (user === null) return <Login />`은 **훅(`use`로 시작하는 `useState`, `useEffect`, `useRecords` 등)을 모두 부른 뒤에** 둔다. React는 이름표 없이 **부르는 순서**로 "몇 번째 `useState`의 값"을 기억한다. 훅 중간에 `return`하면 어떤 때는 훅 5개, 어떤 때는 2개를 불러서 순서가 어긋나고, React가 에러를 낸다. Java에 비슷한 규칙은 없다. 그래서 "화면을 일찍 끝내는 `return`은 항상 훅 아래"로 외워 둔다
- 로그인 화면이 App 안에 있어서 로그아웃 기능은 없다. 한 번 로그인하면 계속 쓴다
- **`useEffect(..., [user])`: `user`가 바뀔 때마다 다시 돈다.** 앱을 열 때(이미 로그인됨) 한 번, 로그인 직후(`null` → 사용자) 한 번이다. 로그인 전이면 아무것도 안 한다
  - `return startSync()`: `startSync`가 돌려주는 함수를 React에 "정리 함수"로 넘긴다. React는 화면이 사라지거나 `user`가 바뀌기 전에 이 함수를 불러 `online`·`visibilitychange` 감시를 멈춘다 (10번). 뒤로 가기의 `popstate` 감시와 같은 짜임이다 → [[2026-10-22-브라우저-history와-뒤로-가기]]
  - 개발 중(`npm run dev`)에는 React의 `StrictMode`가 "켜기 → 정리 → 다시 켜기"를 일부러 한 번 더 해서 `uploadPending()`이 거의 동시에 두 번 불린다. 겹침을 막아 두어서(8번) 같은 기록을 두 번 보내지 않는다


## 8. `data/syncService.ts`: 올리기 (6-4)

6-5에서 내려받기를 더하면서, 올리기와 내려받기가 같이 쓰는 부분(겹침 막기, 인터넷·로그인 확인)을 함수 둘로 뺐다. 올리기가 하는 일은 6-4 때와 같다.

```ts
const DUPLICATE_KEY = '23505'

function oneAtATime(name: string, task: () => Promise<void>): () => Promise<void> {
  let running: Promise<void> | null = null
  let again = false
  return () => {
    if (running !== null) {
      again = true
      return running
    }
    running = (async () => {
      try {
        do {
          again = false
          await task()
        } while (again)
      } catch (e) {
        console.warn(`${name} 실패 (다음에 다시 함)`, e)
      } finally {
        running = null
      }
    })()
    return running
  }
}

async function connectedSupabase() {
  if (!navigator.onLine) return null
  const supabase = getSupabase()
  const { data } = await supabase.auth.getSession()
  return data.session === null ? null : supabase
}

export const uploadPending = oneAtATime('기록 올리기', async () => {
  const pending = await db.records.where('synced').equals(0).toArray()
  if (pending.length === 0) return
  const supabase = await connectedSupabase()
  if (supabase === null) return

  for (const stored of pending) {
    const { error } = await supabase.from('records').insert<FarmRecord>(toRow(stored))
    if (error === null || error.code === DUPLICATE_KEY) {
      await db.records.update(stored.id, { synced: 1 })
    } else {
      console.warn('기록 올리기 실패', stored.id, error)
    }
  }
})

function toRow(stored: StoredRecord): FarmRecord {
  const { synced: _synced, ...record } = stored
  return record
}
```

### 올리기 순서

1. **안 보낸 기록을 색인으로 찾는다.** `where('synced').equals(0)`. 3단계에서 `synced`를 0/1로 둔 이유가 이것이다 → [[2026-10-22-IndexedDB와-Dexie]] 3번. 없으면 Supabase를 부르지도 않는다
2. **`connectedSupabase()`: 인터넷과 로그인 표를 확인한다.** 둘 중 하나라도 안 되면 `null`이고, 그러면 그만한다
   - `navigator.onLine`이 `false`면 끊긴 게 확실하다. `true`라고 꼭 되는 것은 아니라서(와이파이는 잡혔는데 인터넷이 안 되는 경우), 그때는 보내 보고 실패하면 다음에 다시 한다
   - `getSession()`은 로그인 표(JWT)가 지났으면 refresh token으로 새로 받아 온다. 못 받으면(인터넷 끊김, 계정 문제) `session`이 `null`이다 → [[2026-10-23-JWT와-요청-인증]] 2번
3. **한 건씩 `insert`한다.** 결과에 따라 셋 중 하나다

| Supabase 답 | 뜻 | 하는 일 |
|---|---|---|
| `error === null` | 저장됨 | `synced = 1` |
| `error.code === '23505'` | 같은 id가 이미 있음 | **보낸 것으로 보고** `synced = 1` |
| 그 밖의 에러 | 권한(RLS)에 막힘(`42501`), 값이 틀림 등 | 0으로 남겨 두고 다음 기록으로 |

- **`23505`가 "이미 보낸 것"인 이유:** 지난번에 보냈고 서버는 저장했는데, 답이 오기 전에 인터넷이 끊기면 폰은 못 보낸 줄 안다. 다시 보내면 같은 id라 서버가 거절한다. id는 폰에서 만든 UUID라 다른 기록과 겹칠 일이 없으니, 같은 id면 같은 기록이다 (`CLAUDE.md` 동기화 규칙). Spring에서 `DuplicateKeyException`을 잡아 성공으로 치는 것과 같다
- **한 건씩 보내는 이유:** 여러 건을 한 번에 보내면 그중 하나만 `23505`여도 전부 실패한다. 하루에 많아야 수십 건이다 → [[결정기록]] "올리기: 한 건씩 보내고…"
- **에러면 멈추지 않고 다음으로 가는 이유:** 한 건이 계속 막히면(예: 남의 이름) 그 뒤 기록이 영영 안 올라가기 때문이다. 실제로 10월 23일에 그런 기록 한 건이 남아 있었다 (15번)
- **`synced`를 1로 바꾸는 것은 "기록은 고치지 않는다" 규칙과 상관없다.** `synced`는 폰에만 있는 표시이고 서버로 보내지 않는다. 기록 내용은 그대로다
- `supabase.from('records').insert(...)`: JPA의 `repository.save(...)`처럼 보이지만, 실제로는 Supabase의 인터넷 창구로 `POST /rest/v1/records` 요청을 보낸다. 실패해도 예외를 던지지 않고 `error`에 담아 돌려준다 (4번의 `signIn`과 같다)

### `oneAtATime`: 겹쳐 불려도 하나만 돌게

저장 직후·앱 열 때·재연결·화면으로 돌아옴이 거의 동시에 일어날 수 있다. 둘이 같이 돌면 같은 기록을 두 번 보내거나 받는다. 서버(`23505`)와 id 거르기가 막아 주니 망가지지는 않지만 쓸데없는 요청이다.

`oneAtATime(이름, 할 일)`은 **"할 일"을 감싼 새 함수를 돌려준다.** `uploadPending`과 `downloadNew`가 각각 이것으로 만든 함수다. 감싼 함수마다 `running`, `again`을 따로 가진다. 그래서 올리기가 도는 중에 내려받기를 불러도 서로 막지 않는다.

- `running`: 지금 도는 작업. 없으면 `null`
- 도는 중에 또 불리면 새로 시작하지 않고, `again = true`로 "끝나고 한 번 더"만 표시한 뒤 도는 작업을 그대로 돌려준다
- 끝날 때 `again`이 `true`면 한 번 더 돈다(`do ... while`). 그사이 저장되거나 서버에 들어온 기록도 놓치지 않는다
- 에러가 나면 `catch`에서 경고만 찍는다. **그래서 `uploadPending()`, `downloadNew()`는 에러를 던지지 않는다.** 실패하면 다음 기회에 다시 한다
- `finally`에서 `running = null`로 비운다. 에러가 나도 비워져서 다음에 다시 돌 수 있다

**Java라면 락이 필요하지만 여기는 변수 하나로 된다.** JS는 스레드가 하나다. 두 코드가 정말로 동시에 돌지 않고, `await`에서만 차례를 넘긴다. 그래서 `if (running !== null)` 검사와 `running = ...` 사이에 다른 코드가 끼어들 수 없다.

```java
// Java라면: 여러 스레드가 동시에 들어올 수 있어서 원자적으로 바꿔야 한다
class OneAtATime {
  private final AtomicBoolean running = new AtomicBoolean(false);
  private volatile boolean again = false;
  private final Runnable task;

  OneAtATime(Runnable task) { this.task = task; }

  void run() {
    if (!running.compareAndSet(false, true)) { again = true; return; }
    try { do { again = false; task.run(); } while (again); }
    finally { running.set(false); }
  }
}
OneAtATime uploadPending = new OneAtATime(this::uploadOnce);
```

**함수가 변수를 "기억"하는 것(클로저):** `oneAtATime`은 이미 끝났는데, 돌려준 함수는 그 안의 `running`, `again`을 계속 쓴다. JS 함수는 만들어질 때 주변 변수를 붙들고 다닌다. Java로 치면 위 `OneAtATime` 객체의 필드와 같다. 객체를 만드는 대신 함수 하나로 같은 일을 한다.

처음 나오는 문법:

- **`Promise<void>`**: "나중에 끝나는 작업"이다. Java의 `CompletableFuture<Void>`. `await`로 끝날 때까지 기다린다
- **`task: () => Promise<void>`**: "인자 없이 부르면 `Promise<void>`를 돌려주는 함수"라는 타입이다. Java의 `Supplier<CompletableFuture<Void>>`
- **`(async () => { ... })()`**: 이름 없는 `async` 함수를 만들자마자 부른다. 끝에 붙은 `()`가 "지금 부르기"다. 부르면 바로 `Promise`가 돌아오고, 그걸 `running`에 넣는다. Java로 치면 `CompletableFuture.runAsync(() -> { ... })`의 결과를 필드에 넣어 두는 것
- **`` `${name} 실패` ``**: 뒤따옴표(`` ` ``) 글자 안의 `${...}`에 값을 넣는다. Java의 `name + " 실패"`, `String.format("%s 실패", name)`
- **`export const uploadPending = oneAtATime(...)`**: 함수를 `function`으로 선언하지 않고, 함수를 돌려받아 변수에 넣었다. 부르는 쪽은 `uploadPending()`으로 똑같이 부른다
- **`do { } while ()`, `try { } catch { } finally { }`**: Java와 같다
- **`void uploadPending()`**: 돌아오는 `Promise`를 **일부러 기다리지 않는다**는 표시다. `void`가 없어도 동작은 같지만, "깜빡하고 `await`를 빠뜨린 것이 아니다"를 읽는 사람에게 알린다. Java에서 `CompletableFuture.runAsync(...)`를 부르고 `join()`하지 않는 것과 같다. 에러를 던지지 않으니 기다리지 않아도 안전하다
- **`for (const stored of pending)`**: 배열을 하나씩 돈다. Java의 `for (StoredRecord stored : pending)`. `of`가 아니라 `in`을 쓰면 값이 아니라 번호(0, 1, 2…)가 나오니 조심한다
- **`const { synced: _synced, ...record } = stored`**: 객체 나누기(구조 분해)다. `synced`는 `_synced`라는 이름으로 꺼내고(안 쓴다는 뜻으로 `_`를 붙임), **나머지 항목 전부**는 `record`라는 새 객체로 모은다(`...`). 결과로 `synced`만 뺀 기록이 된다. 서버 `records` 테이블에는 `synced` 칸이 없어서 빼고 보내야 한다. Java로 치면 `StoredRecord`에서 필드 하나만 뺀 새 DTO를 만드는 일이다
- **`insert<FarmRecord>(...)`**: 타입 인자를 직접 적었다. 적지 않으면 TypeScript가 기록 종류 여덟 개 중 하나(약)를 골라 타입을 맞추려다 "웃거름 기록에는 `pesticide`가 없다"는 에러를 낸다. Java의 `Collections.<String>emptyList()`처럼 추론 대신 직접 알려 주는 것이다. 기록 종류가 나뉜 타입은 [[2026-10-22-TypeScript-구별된-유니온]]

## 9. `data/syncService.ts`: 내려받기 (6-5)

다른 폰(형 폰)이 올린 기록을 이 폰(아버지 폰)으로 가져온다. 방식을 정한 이유는 [[결정기록]] "내려받기: 5분 겹쳐, 1000건씩 끊어, 폰에 없는 id만".

```ts
const LAST_RECEIVED_KEY = 'buchu-farm:last-received-at'
const OVERLAP_MS = 5 * 60 * 1000
const PAGE_SIZE = 1000

export const downloadNew = oneAtATime('기록 내려받기', async () => {
  const supabase = await connectedSupabase()
  if (supabase === null) return

  const last = readLastReceivedAt()
  const since = last === null ? null : new Date(Date.parse(last) - OVERLAP_MS).toISOString()

  for (let from = 0; ; from += PAGE_SIZE) {
    let query = supabase.from('records').select('*')
    if (since !== null) query = query.gte('received_at', since)
    const { data, error } = await query
      .order('received_at')
      .order('id')
      .range(from, from + PAGE_SIZE - 1)
      .overrideTypes<RecordRow[], { merge: false }>()
    if (error !== null) throw error

    await addMissing(data)
    if (data.length > 0) writeLastReceivedAt(data[data.length - 1].received_at)
    if (data.length < PAGE_SIZE) return
  }
})

async function addMissing(rows: RecordRow[]): Promise<void> {
  const records = rows.flatMap((row) => {
    const r = fromRow(row)
    if (r === null) console.warn('알 수 없는 기록이라 건너뜀', row.id)
    return r === null ? [] : [r]
  })
  if (records.length === 0) return
  await db.transaction('rw', db.records, async () => {
    const existing = await db.records.bulkGet(records.map((r) => r.id))
    const missing = records.filter((_, i) => existing[i] === undefined)
    await db.records.bulkAdd(missing.map((r) => ({ ...r, synced: 1 as const })))
  })
}
```

### 내려받기 순서

1. **인터넷과 로그인 표를 확인한다** (`connectedSupabase`, 8번과 같음)
2. **어디서부터 받을지 정한다.** 폰에 적어 둔 "마지막으로 받은 시각"(`last`)이 있으면 그보다 5분 앞(`since`)부터, 없으면(처음 받는 폰) 처음부터 다 받는다
3. **1000건씩 끊어 받는다.** `received_at`, 같으면 `id` 순서로 줄 세워 0~999번째, 1000~1999번째… 순서가 매번 같아야 끊어 받을 때 빠지거나 겹치는 줄이 없어서, 시각이 같은 줄은 `id`로 한 번 더 줄 세운다
4. **받은 것 중 폰에 없는 id만 넣는다** (`addMissing`). 폰에 넣을 때는 `synced = 1`이다. 이미 서버에 있는 기록이니 다시 올릴 필요가 없다
5. **다 넣은 뒤에 마지막 `received_at`을 적는다.** 넣다가 실패하면 시각을 안 적어서 다음에 같은 곳부터 다시 받는다
6. **1000건보다 적게 왔으면 끝.** 1000건이 꽉 찼으면 다음 1000건을 받으러 간다

**5분 겹치는 이유:** `received_at`은 서버가 저장을 "시작한" 시각이다. 형 폰 기록 A가 01:00:00에 저장을 시작해 01:00:02에 끝나고, 그사이 아버지 폰 기록 B가 01:00:01에 시작해 바로 끝났다고 하자. 01:00:01에 내려받으면 B만 보이고(A는 아직 저장 중), "마지막으로 받은 시각"은 01:00:01이 된다. 다음에 01:00:01부터 받으면 A(01:00:00)를 영영 놓친다. 5분 앞부터 다시 받으면 A가 잡힌다. B는 또 오지만 폰에 있는 id라 걸러진다.

**폰에 있는 기록을 건드리지 않는 이유:** 기록은 추가만 하므로 같은 id면 내용도 같다. 특히 **내가 적었는데 아직 못 보낸 기록**(`synced = 0`)을 서버 것으로 덮어 1로 바꾸면 안 된다. 그래서 "있으면 건너뛰기"만 한다.

**`fromRow`: 서버 한 줄 → 폰 기록.** 서버는 그 종류에 없는 칸도 `null`로 보낸다(웃거름 기록에도 `pesticide: null`). 폰에서 만든 기록에는 그런 칸이 아예 없다. 모양을 같게 하려고 종류(`type`)마다 그 종류의 칸만 남긴다. 꼭 있어야 할 칸이 비었거나(수확 완료인데 `cycle_days`가 없음) 모르는 종류면 `null`을 돌려주고, `addMissing`이 경고를 찍고 건너뛴다. `recorded_at`도 서버 모양(`…123+00:00`)을 폰 모양(`…123Z`)으로 바꾼다.

### 처음 나오는 문법

- **`5 * 60 * 1000`**: 5분을 밀리초로. JS의 시각 계산은 밀리초 단위다 (Java의 `System.currentTimeMillis()`와 같음). `Duration.ofMinutes(5).toMillis()`
- **`Date.parse(last)`**: 시각 글자를 밀리초 숫자로. `new Date(숫자).toISOString()`: 다시 `"2026-10-23T01:00:00.000Z"` 글자로. Java의 `Instant.parse(last).minus(Duration.ofMinutes(5)).toString()`
- **`for (let from = 0; ; from += PAGE_SIZE)`**: 가운데 조건을 비워 둔 반복. 끝은 안에서 `return`으로 낸다. Java의 `for (int from = 0; ; from += PAGE_SIZE)`와 같다
- **`let query = ...; if (...) query = query.gte(...)`**: 조건이 있을 때만 `where`를 붙인다. JPA Criteria나 QueryDSL에서 `if (since != null) builder.and(...)`로 조건을 붙이는 것과 같다
- **Supabase 쿼리 사슬:** 이어 부른 것이 요청 하나가 된다. 실제로는 `GET /rest/v1/records?received_at=gte.…&order=received_at,id` 요청에 "0~999번째"(`Range` 헤더)를 붙여 보낸다
  ```java
  // Spring Data JPA로 치면
  repository.findByReceivedAtGreaterThanEqual(since,
      PageRequest.of(page, 1000, Sort.by("receivedAt", "id")));
  ```
- **`.overrideTypes<RecordRow[], { merge: false }>()`**: 돌아오는 줄의 타입을 알려 준다. 테이블 타입을 따로 만들지 않아서, 적지 않으면 TypeScript가 줄의 모양을 모른다. 실제로 검사하지는 않는다(`as`처럼). 처음엔 `.returns<>()`를 썼는데 "이제 쓰지 말라"(deprecated)는 표시가 있어 바꿨다
- **`if (error !== null) throw error`**: 올리기와 달리 여기서는 던진다. 그러면 `oneAtATime`의 `catch`가 받아 경고를 찍는다. 다음 페이지로 가지 않고, 시각도 안 적힌다
- **`rows.flatMap((row) => ... ? [] : [r])`**: 줄마다 배열을 돌려주고 그 배열들을 이어 붙인다. 빈 배열을 돌려주면 그 줄은 빠진다. "바꾸면서 거르기"를 한 번에 한다. Java의 `rows.stream().flatMap(row -> r == null ? Stream.empty() : Stream.of(r))`
- **`db.transaction('rw', db.records, async () => { ... })`**: 안의 일을 한 묶음으로 한다. 읽고 쓰기(`'rw'`), 대상은 `records` 표. 중간에 실패하면 다 없던 일이 된다. Spring의 `@Transactional`과 같다
- **`bulkGet(ids)`**: id 여러 개를 한 번에 찾는다. 없는 자리는 `undefined`. JPA의 `findAllById`와 비슷하지만, 순서가 넘긴 id 순서 그대로고 없는 자리도 비워 둔다는 점이 다르다. 그래서 `existing[i] === undefined`로 "i번째 기록이 폰에 없다"를 안다
- **`records.filter((_, i) => ...)`**: `filter`는 값과 함께 몇 번째인지(`i`)도 넘겨준다. 값은 안 쓰니 `_`로 받았다
- **`bulkAdd(...)`**: 여러 건을 한 번에 넣는다. JPA의 `saveAll`
- **`synced: 1 as const`**: 그냥 `1`이라 쓰면 TypeScript는 "숫자"로 본다. `synced`의 타입은 `0 | 1`이라 "숫자"는 안 맞는다. `as const`는 "이 값 그대로(1)"라고 알린다
- **`switch (row.type) { case 'spray': ... }`** (`fromRow`): Java의 `switch`와 같다. `case`를 여러 개 이어 쓰면(`top_dressing`, `fertigation`, `harvest_start`) 같은 일을 한다
- **`readLastReceivedAt` / `writeLastReceivedAt`**: localStorage를 `try { } catch { }`로 감쌌다. 개인 정보 보호 모드 등에서 localStorage가 막히면 읽을 때는 "처음 받는 폰"으로, 쓸 때는 그냥 넘어간다. 다음에 처음부터 다시 받아도 id로 걸러져 문제없다

## 10. `startSync`: 언제 주고받나

```ts
async function syncNow(): Promise<void> {
  await uploadPending()
  await downloadNew()
}

export function startSync(): () => void {
  const onOnline = () => void syncNow()
  const onVisible = () => {
    if (document.visibilityState === 'visible') void syncNow()
  }
  window.addEventListener('online', onOnline)
  document.addEventListener('visibilitychange', onVisible)
  void syncNow()
  return () => {
    window.removeEventListener('online', onOnline)
    document.removeEventListener('visibilitychange', onVisible)
  }
}
```

| 언제 | 누가 부르나 | 하는 일 |
|---|---|---|
| 저장 직후 | `recordRepository.addRecord` → `uploadPending()` | 올리기만 |
| 앱을 열 때 (로그인 직후 포함) | `App`의 `useEffect` → `startSync()` → `syncNow()` | 올리기 → 내려받기 |
| 인터넷이 다시 연결될 때 | `online` 이벤트 → `syncNow()` | 올리기 → 내려받기 |
| 앱 화면으로 돌아올 때 (6-5에서 더함) | `visibilitychange` 이벤트 → `syncNow()` | 올리기 → 내려받기 |

- **올리고 나서 내려받는 이유:** 순서가 바뀌어도 틀리지는 않는다(내 기록은 폰에 이미 있어 걸러진다). 먼저 올려 두면 다른 폰이 조금이라도 빨리 받는다
- **`visibilitychange`를 더한 이유:** 홈 화면 앱은 닫아도 꺼지지 않고 뒤에 있다가 다시 보이는 일이 많다. 이게 없으면 형이 적은 기록이 아버지 폰에서는 앱을 완전히 껐다 켤 때까지 안 보인다. `CLAUDE.md` 동기화 규칙에 없던 것이라 빼도 된다 → [[결정기록]] "앱 화면으로 돌아올 때도 주고받는다"
- **`document.visibilityState`**: 화면이 보이면 `'visible'`, 다른 앱으로 가거나 탭을 바꾸면 `'hidden'`. `visibilitychange`는 둘 사이가 바뀔 때마다 오니, 보일 때만 주고받는다
- **`window` vs `document`**: `online`은 브라우저 창(`window`)의 이벤트이고, `visibilitychange`는 페이지 문서(`document`)의 이벤트다. 어디에 붙는 이벤트인지 정해져 있다
- 정리 함수는 두 감시를 다 멈춘다 (7번)
- 시크릿 창에서는 이벤트가 같다. 그래서 PC에서 "일반 창 = 내 폰, 시크릿 창 = 다른 폰"으로 시험할 수 있다 → [[2026-10-23-시크릿-창으로-두-폰-시험하기]]

## 11. 테스트: `syncService.test.ts` (17개)

진짜 Supabase 대신, 보낸 기록을 받아 정해 둔 답을 돌려주는 가짜를 끼운다.

```ts
const { insert, getSession, gte, range, fetchPage } = vi.hoisted(() => ({
  insert: vi.fn(), getSession: vi.fn(), gte: vi.fn(), range: vi.fn(), fetchPage: vi.fn(),
}))
vi.mock('./supabase', () => {
  const query = {
    gte: (...args: unknown[]) => (gte(...args), query),
    order: () => query,
    range: (...args: unknown[]) => (range(...args), query),
    overrideTypes: () => fetchPage(),
  }
  return {
    getSupabase: () => ({ auth: { getSession }, from: () => ({ insert, select: () => query }) }),
  }
})
```

- **`vi.hoisted`**: `vi.mock`은 파일 맨 위로 끌어올려져 `import`보다 먼저 실행된다. 그 안에서 `insert`를 쓰려면 `insert`도 그보다 먼저 만들어져 있어야 해서, `vi.hoisted`로 같이 끌어올린다. Java에는 이런 순서 문제가 없다 (Mockito는 테스트 메서드 안에서 `when(...)`을 부르면 된다)
- **쿼리 사슬 흉내:** `query`의 `gte`, `order`, `range`는 자기 자신(`query`)을 돌려줘서 계속 이어 부를 수 있다. 마지막 `overrideTypes()`가 `fetchPage()`의 답(`{ data, error }`)을 돌려준다. `gte`, `range`에는 무엇으로 불렸는지 기록하는 가짜를 끼워, "5분 앞부터 받았나", "0~999, 1000~1999로 끊었나"를 본다. Mockito의 `RETURNS_SELF`(빌더 흉내)와 같은 생각이다
  - `(gte(...args), query)`: 쉼표로 이은 식은 앞의 것을 하고 **마지막 값**을 돌려준다. "기록하고 나서 `query`를 돌려줘라"를 한 줄로 쓴 것
  - `(...args: unknown[])`: 받은 인자를 몽땅 배열로 받는다. Java의 `Object... args`
- **`mockResolvedValue(값)`**: `await` 하면 그 값이 나오는 가짜. Mockito의 `when(insert(any())).thenReturn(CompletableFuture.completedFuture(OK))`
  - `mockResolvedValueOnce(A).mockResolvedValueOnce(B)`: 첫 번째는 A, 두 번째는 B. Mockito의 `thenReturn(A, B)`
  - `mockRejectedValue(에러)`: `await` 하면 예외가 나는 가짜 (인터넷이 끊긴 흉내). `thenThrow(...)`
  - `mockImplementationOnce(함수)`: 첫 번째로 불릴 때 그 함수를 대신 돌린다. "보내는 도중에 새 기록이 저장되는" 상황을 만들 때 썼다. Mockito의 `thenAnswer(...)`
- **`vi.stubGlobal('navigator', { onLine: true })`**: 테스트(Node)의 `navigator`에는 `onLine`이 없다(`undefined`). 그러면 `!navigator.onLine`이 `true`라 아무것도 안 한다. 그래서 "인터넷 됨"으로 바꿔 끼운다. "인터넷 끊김" 테스트에서는 `{ onLine: false }`로. localStorage도 테스트에는 없어서 `Map`으로 만든 가짜를 끼운다
- **`Promise.all([a(), b(), c()])`**: 셋을 거의 동시에 시작하고 모두 끝날 때까지 기다린다. "겹쳐 불러도 한 번만 보낸다" 테스트에서 썼다. Java의 `CompletableFuture.allOf(a, b, c).join()`
- `vi.spyOn(console, 'warn').mockImplementation(() => {})`: 실패 테스트에서 찍히는 경고 글을 숨긴다. 결과 화면이 지저분해지지 않게

## 13. 하나 따라가 보기: 하우스에서 3동 약 저장 → 올리기

인터넷이 끊긴 하우스에서 저장하고, 나와서 인터넷이 잡히는 경우다.

1. 3동 약 [저장] → `addRecord` → `recorded_by` = 로그인한 사람 id, `synced: 0`으로 IndexedDB에 저장
2. `void uploadPending()` → `running`이 비어 있어 새로 시작 → 안 보낸 기록 1건 → `connectedSupabase()` → `navigator.onLine`이 `false` → `null` → 그만. `addRecord`는 이미 끝나서 화면은 목록으로 돌아가 "3동 약 저장했어요"
3. 하우스를 나와 인터넷이 잡힌다 → 브라우저가 `online` 이벤트 → `startSync`가 등록해 둔 `onOnline` → `syncNow()` → `uploadPending()`
4. 안 보낸 기록 1건 → `connectedSupabase()` → `getSession()`이 지난 JWT를 새로 받아 온다
5. `insert(toRow(기록))` → 요청에 JWT가 붙는다 → Supabase가 GRANT(로그인함, 추가 가능) → RLS(`recorded_by` = `auth.uid()`) 검사 → 저장. `received_at`은 서버 시각으로 채워진다
6. `error === null` → `synced = 1`. 다음에 올리기가 돌아도 이 기록은 다시 안 보낸다
7. 이어서 `downloadNew()` → 방금 올린 3동 약도 서버에서 내려오지만, 폰에 있는 id라 걸러진다
8. 5번에서 답이 오기 전에 인터넷이 또 끊겼다면 → 기록은 서버에 있는데 폰은 0 그대로 → 다음 올리기에서 `23505` → "이미 보낸 것"으로 1

화면은 1~8 내내 IndexedDB를 보고 그린다. 올리기가 되든 안 되든 목록은 똑같다. "미전송 N건" 표시는 6-6에서 한다.

## 14. 하나 따라가 보기: 형 폰의 기록이 아버지 폰에 보이기까지

형이 5동에 웃거름을 적었다. 아버지 폰은 홈 화면 앱이 뒤에 있는 상태다. 시각은 예시 값이다.

1. 형 폰: 5동 웃거름 [저장] → 13번처럼 올라간다. 서버가 `received_at` = `10:00:00`을 채운다
2. 아버지 폰에는 지난번에 받은 마지막 시각 `09:30:00`이 적혀 있다
3. 아버지가 앱을 다시 본다 → `visibilitychange` → `visibilityState === 'visible'` → `syncNow()`
4. `uploadPending()`: 아버지 폰에 안 보낸 기록이 없으면 Supabase를 부르지도 않고 끝
5. `downloadNew()`: `since` = `09:30:00` − 5분 = `09:25:00` → "`09:25:00` 이후 기록, 0~999번째" 요청
6. 서버가 `09:25:00` 이후 기록을 돌려준다: 아버지가 09:28에 올린 기록(겹쳐 받은 것) + 형의 5동 웃거름
7. `addMissing`: `bulkGet`으로 찾아보니 09:28 기록은 폰에 있고 5동 웃거름은 없다 → 5동 웃거름만 `synced = 1`로 넣는다
8. 마지막 시각을 `10:00:00`으로 적는다. 2건 < 1000건이라 끝
9. `useLiveQuery`가 기록이 늘어난 것을 알아채 목록을 다시 그린다 → 5동에 웃거름이 보인다

아버지 폰이 하우스 안이라 인터넷이 끊겨 있었다면 5번에서 그만한다. 나와서 인터넷이 잡히면(`online`) 그때 받는다.

| 시험 기록 지우기 (제대로 쓰는 날) | 코드 아님. ① 쓰던 기기를 모두 인터넷 되는 곳에서 열어 안 보낸 기록을 올림 → ② Supabase → SQL Editor에서 `delete from records;` (SQL Editor는 관리자로 실행되어 RLS를 거치지 않는다) → ③ 기기마다 앱 저장 데이터를 지우고 다시 로그인. 서버에서 지워도 폰에 내려간 기록은 안 지워져서 ③이 필요하다 → [[결정기록]] "시험 기록은 제대로 쓰는 날 서버와 기기를 한꺼번에 비운다" |
