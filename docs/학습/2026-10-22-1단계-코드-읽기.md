# 1단계 코드 읽기: 기록 타입과 계산

앱 1단계에서 만들고 2.5단계에서 고친 `src/domain/` 파일을 하나씩 읽는다. 문법과 도구 설명은 개념 노트에 있다. 이 노트는 **"이 파일이 무슨 일을 하고, 왜 이렇게 짰나"**를 다룬다.

- TypeScript 타입 문법 → [[2026-10-22-TypeScript-구별된-유니온]]
- 순수 함수, 날짜 계산, 테스트 → [[2026-10-22-Vitest-테스트와-순수-함수]]

> **2.5단계에서 바뀐 것 (2026-10-22):** 처음에는 약 기록의 "수확 전 일수"로 🔴 약 대기 D-n을 계산했다. 예외가 많아 자동 판단을 없애고 **수확 후·약 후 며칠 지났는지**와 🟢 수확 가능만 계산하도록 바꿨다. `sprayClearDate`, `nextHarvestDate` 함수가 없어지고 `lastOf`가 생겼다. → [[결정기록]] "앱은 약 대기·수확 가능을 자동 판단하지 않고 경과 일수를 보여준다"

## 1. 파일 지도

```
src/
├ config/farm.ts           농장 기본값 (수확 가능까지 35일). 입력 화면(3단계)에서 쓴다
└ domain/
   ├ types.ts              기록 모양 정의 (FarmRecord)
   ├ harvestCalc.ts        계산. types.ts만 가져다 쓴다
   └ harvestCalc.test.ts   harvestCalc.ts를 검사
```

화살표는 "가져다 쓴다(import)"는 뜻이다.

```
harvestCalc.test.ts ──→ harvestCalc.ts ──→ types.ts
         └────────────────────────────────→ types.ts
```

**`domain/` 폴더는 화면, DB, 서버를 전혀 모른다.** React도, Dexie도, Supabase도 import하지 않는다. Spring으로 치면 `@Service`나 `@Repository`가 아닌 순수 도메인 클래스 패키지다. 그래서 브라우저 없이 테스트할 수 있고, 인터넷이 끊겨도 계산이 된다.

## 2. `types.ts`: 기록의 모양

기록 여섯 종류를 `type` 필드 값으로 구분하는 하나의 타입 `FarmRecord`로 묶었다. 문법은 [[2026-10-22-TypeScript-구별된-유니온]]에 자세히 있다.

| 타입 | `type` | 종류마다 다른 항목 |
|---|---|---|
| `SprayRecord` | `'spray'` | `pesticide` (약 이름) |
| `TopDressingRecord` | `'top_dressing'` | 없음 |
| `FertigationRecord` | `'fertigation'` | 없음 |
| `HarvestRecord` | `'harvest'` | `cycle_days` (수확 가능까지 일수) |
| `HarvestAmountRecord` | `'harvest_amount'` | `target_id`(수확 기록 id), `boxes`, `bunches` |
| `CancelRecord` | `'cancel'` | `target_id`(취소할 기록 id) |

이 파일에서 볼 점:

- **필드 이름이 `house_no`, `work_date`처럼 밑줄 표기다.** TS에서는 보통 `houseNo`처럼 쓰지만, Supabase `records` 테이블 컬럼 이름과 똑같이 맞췄다. 6단계에서 서버와 주고받을 때 이름을 바꾸는 변환 코드가 필요 없다. (Java에서 JPA `@Column(name = "house_no")`로 이름을 이어 주는 일을 아예 안 하려는 것)
- **`work_date: string`**: 날짜를 `Date` 객체가 아닌 `"YYYY-MM-DD"` 글자로 둔다 (`CLAUDE.md` 데이터 규칙). 이유는 Vitest 노트 2번
- **`cycle_days`가 수확 기록 안에 있다**: 기본값(35일)을 계산할 때마다 읽지 않고, 수확을 기록할 때 값을 함께 저장한다. 나중에 기본값을 바꿔도 지난 수확의 계산이 달라지지 않는다 → [[결정기록]] "🟢 수확 가능은 수확 가능까지 일수가 지나면 뜬다"
- **수확량이 수확 기록과 따로 있다**: 수확량은 다음 날 아침에 알기 때문이다. 기록은 고치지 않고 추가만 하므로, 나중에 `HarvestAmountRecord`를 새로 추가해 수확 기록에 덧붙인다. 박스와 단은 환산하지 않고 따로 둔다 → [[결정기록]] "수확량은 박스·단으로, 다음 날 따로 입력"

## 3. `harvestCalc.ts`: 계산

파일 안에서 위에서 아래로 쌓아 올리는 구조다. 아래 함수가 위 함수를 부른다.

| 순서 | 함수 | 하는 일 | 공개 |
|---|---|---|---|
| 1 | `toDayNumber`, `fromDayNumber` | 날짜 글자 ↔ "1970-01-01부터 며칠째" 정수 | 파일 안에서만 |
| 2 | `addDays`, `daysBetween` | 날짜 더하기, 두 날짜 사이 일수 | `export` |
| 3 | `activeRecords` | 취소된 기록과 취소 기록을 빼고 "살아 있는" 기록만 남김 | `export` |
| 4 | `isLater` | 두 기록 중 어느 쪽이 나중인지 | 파일 안에서만 |
| 5 | `lastOf` | 조건에 맞는 마지막 기록 하나 찾기 | 파일 안에서만 |
| 6 | `getHouseStatus` | 🟢/⚪ 상태, 수확 후·약 후 일수, 수확 가능일 | `export` (화면에서 씀) |

`export`가 없는 함수는 이 파일 안에서만 쓴다 (Java의 `private`). `export`가 붙어 있으면 다른 파일과 테스트에서 쓸 수 있다.

### 3-1. `activeRecords`: 취소 처리

```ts
export function activeRecords(records: readonly FarmRecord[]): FarmRecord[] {
  const cancelIds = new Set(records.filter((r) => r.type === 'cancel').map((r) => r.id))
  const canceledIds = new Set(
    records
      .filter((r) => r.type === 'cancel')
      .map((r) => r.target_id)
      .filter((targetId) => !cancelIds.has(targetId)),
  )
  return records.filter((r) => r.type !== 'cancel' && !canceledIds.has(r.id))
}
```

세 단계로 읽는다.

1. `cancelIds`: **취소 기록 자신의 id** 모음
2. `canceledIds`: 취소 기록이 가리키는 `target_id` 모음. 단, 가리키는 대상이 또 다른 취소 기록이면 뺀다 (`CLAUDE.md`: "`cancel` 기록은 취소할 수 없다")
3. 결과: 취소 기록이 아니고, 취소당하지도 않은 기록만 남긴다

- `new Set(...)`은 중복 없는 모음이고 `.has(x)`로 들어 있는지 본다. Java의 `HashSet`과 `contains`다
- `!`는 "아니다"(Java와 같음)
- `.map((r) => r.target_id)`: `target_id`는 취소 기록에만 있는 필드인데 에러가 나지 않는다. 바로 앞의 `.filter((r) => r.type === 'cancel')`을 TS가 **타입 가드로 알아서 추론**해서, 그 뒤의 `r`을 `CancelRecord`로 보기 때문이다 (TypeScript 5.5부터 되는 기능). 아래 `getHouseStatus`에서는 `(r): r is HarvestRecord =>`처럼 타입 가드를 직접 적었다. 조건이 `r.type === 'harvest' && r.house_no === houseNo` 두 개라서, 결과가 false여도 "다른 동의 수확 기록"일 수 있다. 이렇게 false가 "수확 기록이 아니다"를 뜻하지 않으면 TS가 추론하지 못하기 때문에 직접 적어야 한다
- `target_id`가 없는 id를 가리키는 경우: `canceledIds`에 들어가도 그 id를 가진 기록이 없으니 아무것도 빠지지 않는다. 그래서 따로 처리하는 코드가 없다
- 수확량 기록(`harvest_amount`)도 `target_id`가 있지만 `type`이 `'cancel'`이 아니라서 여기서는 취소로 보지 않는다

Java Stream으로 쓰면 이렇다.

```java
Set<String> cancelIds = records.stream()
    .filter(r -> r instanceof CancelRecord).map(FarmRecord::id).collect(toSet());
Set<String> canceledIds = records.stream()
    .filter(r -> r instanceof CancelRecord).map(r -> ((CancelRecord) r).targetId())
    .filter(t -> !cancelIds.contains(t)).collect(toSet());
return records.stream()
    .filter(r -> !(r instanceof CancelRecord) && !canceledIds.contains(r.id())).toList();
```

### 3-2. `isLater`: 어느 쪽이 "마지막" 기록인가

```ts
function isLater(a: FarmRecord, b: FarmRecord): boolean {
  if (a.work_date !== b.work_date) return a.work_date > b.work_date
  return Date.parse(a.recorded_at) > Date.parse(b.recorded_at)
}
```

- 먼저 **작업 날짜**로 비교한다. 날짜 글자는 그대로 크기 비교가 된다 (Vitest 노트 2번)
- 같은 날이면 **입력한 시각**으로 비교한다. 같은 날 수확을 두 번 기록했다면 나중에 입력한 쪽의 `cycle_days`를 쓰기 위해서다
- 입력 시각은 `Date.parse`로 밀리초 숫자로 바꿔 비교한다. `"2026-10-01T09:00:00Z"`와 `"2026-10-01T18:00:00+09:00"`은 같은 순간인데 글자로 비교하면 다르게 나온다. 폰마다 시간대 표기가 다를 수 있어서 숫자로 바꾼다. Java로 치면 `OffsetDateTime.parse(...).toInstant()`끼리 비교하는 것이다

### 3-3. `lastOf`: 조건에 맞는 마지막 기록

```ts
function lastOf<T extends FarmRecord>(
  records: readonly FarmRecord[],
  isTarget: (r: FarmRecord) => r is T,
): T | null {
  let last: T | null = null
  for (const r of activeRecords(records)) {
    if (isTarget(r) && (last === null || isLater(r, last))) last = r
  }
  return last
}
```

"마지막 수확 기록"과 "마지막 약 기록"을 찾는 일이 똑같아서 하나로 만들었다.

- `<T extends FarmRecord>`: **제네릭**이다. Java와 문법이 거의 같다 (`<T extends FarmRecord> T lastOf(...)`). 마지막 수확 기록을 찾으면 `T`가 `HarvestRecord`가 되어, 돌려받은 값에서 `cycle_days`를 바로 쓸 수 있다
- `isTarget: (r: FarmRecord) => r is T`: **함수를 인자로 받는다.** "기록을 받아서 T인지 알려 주는 함수"라는 타입이다. Java의 `Predicate<FarmRecord>`와 비슷한데, 결과가 true면 그 기록이 T라는 것까지 TS에 알려 준다
- `let`은 나중에 값을 바꿀 수 있는 변수, `const`는 못 바꾸는 변수다 (Java의 일반 변수와 `final`)
- `for (const r of ...)`는 Java의 `for (FarmRecord r : ...)`
- `activeRecords`를 먼저 거치므로 **취소된 기록은 절대 "마지막"이 되지 않는다**

Java로 쓰면 이런 모양이다.

```java
<T extends FarmRecord> Optional<T> lastOf(List<FarmRecord> records, Class<T> type, Predicate<T> cond) {
  return activeRecords(records).stream()
      .filter(type::isInstance).map(type::cast).filter(cond)
      .max(BY_WORK_DATE_THEN_RECORDED_AT);   // isLater에 해당하는 Comparator
}
```

### 3-4. `getHouseStatus`: 상태와 경과 일수

```ts
export function getHouseStatus(records: readonly FarmRecord[], houseNo: number, today: string): HouseStatus {
  const harvest = lastOf(records, (r): r is HarvestRecord => r.type === 'harvest' && r.house_no === houseNo)
  const spray = lastOf(records, (r): r is SprayRecord => r.type === 'spray' && r.house_no === houseNo)
  const daysSinceSpray = spray === null ? null : daysBetween(spray.work_date, today)

  if (harvest === null) {
    return { kind: 'no_record', daysSinceHarvest: null, daysSinceSpray, readyDate: null }
  }
  const readyDate = addDays(harvest.work_date, harvest.cycle_days)
  return {
    kind: today >= readyDate ? 'ready' : 'growing',
    daysSinceHarvest: daysBetween(harvest.work_date, today),
    daysSinceSpray,
    readyDate,
  }
}
```

- **약 기록은 상태(`kind`)에 아무 영향을 주지 않는다.** 며칠 지났는지(`daysSinceSpray`)만 센다. 약 때문에 벨 수 있는지는 사람이 판단한다
- `spray === null ? null : ...`: 삼항 연산자 (Java와 같음). 약 기록이 없으면 일수도 없다
- `daysBetween(harvest.work_date, today)`: 오늘 수확했으면 0, 어제면 1. 화면에서 0은 "오늘 수확"으로 보여준다
- `today >= readyDate` (`>`가 아님): 수확 가능일 **당일부터** 🟢. 이 한 글자로 하루가 달라져서 테스트로 지키고 있다
- `{ ..., daysSinceSpray, readyDate }`: `daysSinceSpray: daysSinceSpray`의 줄임 표현이다 (이름이 같으면 한 번만 쓴다)
- 수확 기록이 없으면 ⚪ `no_record`. 약·비료 기록만 있어도 자랐는지 판단할 근거가 없으니 🟢을 띄우지 않는다 → [[결정기록]] "수확 기록이 없는 동은 기록 없음(⚪)으로 표시"
- `readyDate`(수확 가능일)는 화면에 직접 보이지 않지만 목록 정렬에 쓴다 ([[2026-10-22-2단계-코드-읽기]] 8번)

결과 모양(`HouseStatus`):

| 필드 | 뜻 | 없으면 |
|---|---|---|
| `kind` | `'ready'` 🟢 / `'growing'` (표시 없음) / `'no_record'` ⚪ | - |
| `daysSinceHarvest` | 마지막 수확 후 며칠 | 수확 기록 없음 → `null` |
| `daysSinceSpray` | 마지막 약 후 며칠 | 약 기록 없음 → `null` |
| `readyDate` | 수확 가능일 | 수확 기록 없음 → `null` |

## 4. 하나 따라가 보기

오늘이 `2026-10-21`이고 1번 동 기록이 이렇다고 하자.

| id | 종류 | 날짜 | 내용 |
|---|---|---|---|
| h1 | 수확 | 09-10 | 수확 가능까지 35일 |
| m | 수확량 | 09-11 | h1의 수확량, 3박스 5단 |
| h2 | 수확 | 10-01 | 35일 (잘못 입력) |
| c | 취소 | 10-01 | `target_id: 'h2'` |
| a | 약 | 10-18 | |

1. `activeRecords` → `cancelIds = {c}`, `canceledIds = {h2}` → 남는 기록: h1, m, a
2. `lastOf`(수확) → h1. m은 수확량 기록이라 수확 기록으로 세지 않는다
3. `lastOf`(약) → a → 약 후 **3일**
4. 수확 가능일 = 09-10 + 35일 = 10-15. 오늘 10-21 ≥ 10-15 → **🟢 수확 가능, 수확 후 41일**

h2를 취소하지 않았다면 "수확 후 20일"이 되고 🟢가 뜨지 않았을 것이다. 잘못 입력한 기록을 지우지 않고 취소 기록을 추가하는 방식이 이렇게 동작한다. → [[결정기록]] "기록은 추가만 하고 수정·삭제하지 않는다"

## 5. `harvestCalc.test.ts`: 무엇을 지키나

테스트 쓰는 법은 [[2026-10-22-Vitest-테스트와-순수-함수]] 3번에 있다. 이 파일에서 볼 점은 **테스트가 `CLAUDE.md` 규칙을 하나씩 지키고 있다**는 것이다.

| `CLAUDE.md` 규칙 | 지키는 테스트 |
|---|---|
| `cancel` 기록은 취소할 수 없다, 없는 `target_id`는 무시 | `activeRecords` 묶음 |
| 수확 가능일 당일부터 🟢 | "수확 가능일 당일이면 🟢 수확 가능", "하루 전이면 아직 자라는 중" |
| 기본값이 아니라 기록에 적힌 `cycle_days`로 계산 | "기본값이 아니라 그 수확 기록에 적힌 일수를 쓴다" |
| 당일은 0일 | "오늘 수확하면 수확 후 0일", "오늘 약을 치면 약 후 0일" |
| 앱은 약 때문에 벨 수 있는지 판단하지 않는다 | "약을 쳐도 수확 가능 판단은 바뀌지 않는다" |
| 수확 기록이 없으면 ⚪ | "약·웃거름·관비 기록만 있으면 ⚪ 수확 기록 없음" |
| 같은 날 기록이 둘이면 나중에 입력한 것 | "같은 날 수확 기록이 둘이면…", "시간대 표기가 달라도…" |

규칙을 바꿀 일이 생기면 이 테스트부터 고친다. 테스트가 실패하는 걸 보고 코드를 고치면 바꾼 규칙이 정말 반영됐는지 확인할 수 있다.

## 6. 이걸 바꾸려면 어디를 고치나

| 바꿀 것 | 고칠 곳 |
|---|---|
| 수확 가능까지 일수 기본값 (35일) | `config/farm.ts`의 `DEFAULT_CYCLE_DAYS`. 앞으로 입력하는 수확 기록부터 적용된다 |
| 🟢이 뜨는 날 (당일부터 / 다음 날부터) | `getHouseStatus`의 `today >= readyDate` + 해당 테스트 |
| 경과 일수 세는 방식 (당일 0일) | `getHouseStatus`의 `daysBetween(...)` + 해당 테스트. 화면 문구는 `HouseList.tsx`의 `ElapsedLine` |
| "마지막 기록"을 고르는 기준 | `isLater` |
| 기록 종류 추가 | `types.ts`의 `RecordType`, 새 `interface`, `FarmRecord` 목록 + Supabase `records` 테이블의 `check` 조건 (`CLAUDE.md`) |
