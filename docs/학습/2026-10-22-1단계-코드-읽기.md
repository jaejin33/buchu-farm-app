# 1단계 코드 읽기: 수확 가능일 계산

앱 1단계(커밋 `863b6b0`)에서 만든 파일을 하나씩 읽는다. 문법과 도구 설명은 개념 노트에 있다. 이 노트는 **"이 파일이 무슨 일을 하고, 왜 이렇게 짰나"**를 다룬다.

- TypeScript 타입 문법 → [[2026-10-22-TypeScript-구별된-유니온]]
- 순수 함수, 날짜 계산, 테스트 → [[2026-10-22-Vitest-테스트와-순수-함수]]

## 1. 파일 지도

```
src/domain/
├ types.ts              기록 모양 정의 (FarmRecord)
├ harvestCalc.ts        계산. types.ts만 가져다 쓴다
└ harvestCalc.test.ts   harvestCalc.ts를 검사 (테스트 35개)
```

화살표는 "가져다 쓴다(import)"는 뜻이다.

```
harvestCalc.test.ts ──→ harvestCalc.ts ──→ types.ts
         └────────────────────────────────→ types.ts
```

**`domain/` 폴더는 화면, DB, 서버를 전혀 모른다.** React도, Dexie도, Supabase도 import하지 않는다. Spring으로 치면 `@Service`나 `@Repository`가 아닌 순수 도메인 클래스 패키지다. 그래서 브라우저 없이 테스트할 수 있고, 인터넷이 끊겨도 계산이 된다.

## 2. `types.ts`: 기록의 모양

기록 다섯 종류(약, 웃거름, 관비, 수확, 취소)를 `type` 필드 값으로 구분하는 하나의 타입 `FarmRecord`로 묶었다. 문법은 [[2026-10-22-TypeScript-구별된-유니온]]에 자세히 있다.

이 파일에서 볼 점:

- **필드 이름이 `house_no`, `work_date`처럼 밑줄 표기다.** TS에서는 보통 `houseNo`처럼 쓰지만, Supabase `records` 테이블 컬럼 이름과 똑같이 맞췄다. 6단계에서 서버와 주고받을 때 이름을 바꾸는 변환 코드가 필요 없다. (Java에서 JPA `@Column(name = "house_no")`로 이름을 이어 주는 일을 아예 안 하려는 것)
- **`work_date: string`**: 날짜를 `Date` 객체가 아닌 `"YYYY-MM-DD"` 글자로 둔다 (`CLAUDE.md` 데이터 규칙). 이유는 Vitest 노트 2번
- **`phi_days`가 약 기록 안에 있다**: 약 목록에서 매번 찾아보지 않고, 입력할 때 값을 복사해 둔다. 나중에 약 정보가 바뀌어도 지난 기록의 계산이 달라지지 않는다 → [[결정기록]] "약 기록에는 수확 전 일수를 복사해 저장한다"
- **`HarvestRecord`의 `amount`가 `number | null`**: 수확량 항목이 아직 미확정이라 비워 둘 수 있게 했다

## 3. `harvestCalc.ts`: 계산

파일 안에서 위에서 아래로 쌓아 올리는 구조다. 아래 함수가 위 함수를 부른다.

| 순서 | 함수 | 하는 일 | 쓰는 곳 |
|---|---|---|---|
| 1 | `toDayNumber`, `fromDayNumber` | 날짜 글자 ↔ "1970-01-01부터 며칠째" 정수 | 2번 |
| 2 | `addDays`, `daysBetween` | 날짜 더하기, 두 날짜 사이 일수 | 4~6번 |
| 3 | `activeRecords` | 취소된 기록과 취소 기록을 빼고 "살아 있는" 기록만 남김 | 4, 5번 |
| 4 | `sprayClearDate` | 약 때문에 벨 수 있는 날 | 6번 |
| 5 | `nextHarvestDate` | 다음 수확 예정일 | 6번 |
| 6 | `getHouseStatus` | 🔴🟡🟢⚪ 상태와 D-n | 화면 (2단계) |

`toDayNumber`, `fromDayNumber`는 앞에 `export`가 없다. 이 파일 안에서만 쓰는 함수다 (Java의 `private`). 나머지는 `export`가 붙어 있어서 다른 파일과 테스트에서 쓸 수 있다.

### 3-1. `activeRecords`: 취소 처리

```ts
export function activeRecords(records: readonly FarmRecord[]): FarmRecord[] {
  const cancelIds = new Set(records.filter((r) => r.type === 'cancel').map((r) => r.id))
  const canceledIds = new Set(
    records
      .filter((r) => r.type === 'cancel')
      .map((r) => r.target_id)
      .filter((targetId) => !cancelIds.has(targetId)),
  )
  return records.filter((r) => r.type !== 'cancel' && !canceledIds.has(r.id))
}
```

세 단계로 읽는다.

1. `cancelIds`: **취소 기록 자신의 id** 모음
2. `canceledIds`: 취소 기록이 가리키는 `target_id` 모음. 단, 가리키는 대상이 또 다른 취소 기록이면 뺀다 (`CLAUDE.md`: "`cancel` 기록은 취소할 수 없다")
3. 결과: 취소 기록이 아니고, 취소당하지도 않은 기록만 남긴다

- `new Set(...)`은 중복 없는 모음이고 `.has(x)`로 들어 있는지 본다. Java의 `HashSet`과 `contains`다
- `!`는 "아니다"(Java와 같음)
- `.map((r) => r.target_id)`: `target_id`는 취소 기록에만 있는 필드인데 에러가 나지 않는다. 바로 앞의 `.filter((r) => r.type === 'cancel')`을 TS가 **타입 가드로 알아서 추론**해서, 그 뒤의 `r`을 `CancelRecord`로 보기 때문이다 (TypeScript 5.5부터 되는 기능). `sprayClearDate`에서는 `(r): r is SprayRecord =>`처럼 타입 가드를 직접 적었다. 조건이 `r.type === 'spray' && r.house_no === houseNo` 두 개라서, 결과가 false여도 "다른 동의 약 기록"일 수 있다. 이렇게 false가 "약 기록이 아니다"를 뜻하지 않으면 TS가 추론하지 못하기 때문에 직접 적어야 한다
- `target_id`가 없는 id를 가리키는 경우: `canceledIds`에 들어가도 그 id를 가진 기록이 없으니 아무것도 빠지지 않는다. 그래서 따로 처리하는 코드가 없다

Java Stream으로 쓰면 이렇다.

```java
Set<String> cancelIds = records.stream()
    .filter(r -> r instanceof CancelRecord).map(FarmRecord::id).collect(toSet());
Set<String> canceledIds = records.stream()
    .filter(r -> r instanceof CancelRecord).map(r -> ((CancelRecord) r).targetId())
    .filter(t -> !cancelIds.contains(t)).collect(toSet());
return records.stream()
    .filter(r -> !(r instanceof CancelRecord) && !canceledIds.contains(r.id())).toList();
```

### 3-2. `sprayClearDate`: 가장 늦은 날 찾기

```ts
let latest: string | null = null
for (const s of sprays) {
  const clear = addDays(s.work_date, s.phi_days)
  if (latest === null || clear > latest) latest = clear
}
return latest
```

- `let`은 나중에 값을 바꿀 수 있는 변수, `const`는 못 바꾸는 변수다 (Java의 일반 변수와 `final`)
- `for (const s of sprays)`는 Java의 `for (SprayRecord s : sprays)`
- `clear > latest`: 날짜 글자를 바로 크기 비교한다. `"YYYY-MM-DD"`라서 가능하다 (Vitest 노트 2번)
- 약을 여러 번 쳤으면 **가장 늦게 풀리는 날**이 기준이다. 오래 가는 약을 먼저 치고 짧은 약을 나중에 쳐도 안전하게 계산된다

`nextHarvestDate`도 같은 모양이다. 가장 늦은 수확일을 찾아 수확 주기(기본 35일)를 더한다.

### 3-3. `getHouseStatus`: 우선순위대로 하나 고르기

```ts
const base = { sprayClearDate: clear, nextHarvestDate: next }

if (clear !== null && today < clear) {
  return { kind: 'spray_wait', daysLeft: daysBetween(today, clear), ...base }
}
if (next === null) {
  return { kind: 'no_record', daysLeft: null, ...base }
}
if (today < next) {
  return { kind: 'growing', daysLeft: daysBetween(today, next), ...base }
}
return { kind: 'ready', daysLeft: null, ...base }
```

- **위에서부터 먼저 맞는 것을 돌려준다.** 그래서 `if`의 순서가 곧 `CLAUDE.md`의 상태 우선순위다. 약 대기(🔴)가 맨 위에 있어서, 수확 기록이 없어도 약 대기 중이면 🔴가 뜬다
- `...base`: 전개 문법으로 `base`의 두 필드를 결과에 함께 넣는다. 네 군데에 똑같이 쓰는 걸 한 번만 적으려고 했다
- `today < clear` (`<=`가 아님): 벨 수 있는 날 **당일에는 약 대기가 아니다.** 이 한 글자가 하루 차이를 만들고, 그 하루가 약 안전 기간이다. 테스트로 지키고 있다

## 4. 하나 따라가 보기

오늘이 `2026-10-21`이고 1번 동 기록이 이렇다고 하자.

| id | 종류 | 날짜 | 내용 |
|---|---|---|---|
| h | 수확 | 09-21 | |
| a | 약 | 10-18 | 수확 전 7일 |
| w | 약 | 10-20 | 수확 전 14일 (잘못 입력) |
| c | 취소 | 10-20 | `target_id: 'w'` |

1. `activeRecords` → `cancelIds = {c}`, `canceledIds = {w}` → 남는 기록: h, a
2. `sprayClearDate` → a만 남았다: 10-18 + 7일 = **10-25** (w가 살아 있었다면 11-03)
3. `nextHarvestDate` → h: 09-21 + 35일 = **10-26**
4. `getHouseStatus` → 오늘 10-21 < 10-25 이므로 **🔴 약 대기, D-4**

w를 취소하지 않았다면 D-13이 떴을 것이다. 잘못 입력한 기록을 지우지 않고 취소 기록을 추가하는 방식이 이렇게 동작한다. → [[결정기록]] "기록은 추가만 하고 수정·삭제하지 않는다"

## 5. `harvestCalc.test.ts`: 무엇을 지키나

테스트 쓰는 법은 [[2026-10-22-Vitest-테스트와-순수-함수]] 3번에 있다. 이 파일에서 볼 점은 **테스트가 `CLAUDE.md` 규칙을 하나씩 지키고 있다**는 것이다.

| `CLAUDE.md` 규칙 | 지키는 테스트 (`describe` 묶음) |
|---|---|
| `cancel` 기록은 취소할 수 없다 | `activeRecords` |
| 없는 `target_id`는 무시 | `activeRecords` |
| 살포일 + `phi_days`가 가장 늦은 날 | `sprayClearDate` |
| 상태 우선순위 🔴 → 🟡 → 🟢, ⚪ 기준 | `getHouseStatus` |
| 벨 수 있는 날 당일은 약 대기 아님 | `getHouseStatus` |

규칙을 바꿀 일이 생기면 이 테스트부터 고친다. 테스트가 실패하는 걸 보고 코드를 고치면 바꾼 규칙이 정말 반영됐는지 확인할 수 있다.
