- 이유: PWA의 오프라인 기능(서비스 워커)은 `https://` 주소나 `localhost`에서만 동작해서, 폰에서 `http://192.168...`로는 시험할 수 없다. 개발자 폰이 아이폰이라 USB로 연결해 폰에서 `localhost`로 여는 방법(안드로이드 크롬 전용)을 쓸 수 없다. Claude가 터널 도구(cloudflared)로 임시 https 주소를 만드는 방법을 추천했지만, 개발자가 "어차피 안 쓸 건데"라며 Vercel에 바로 배포하기로 했다. 지금은 서버와 비밀 키가 없고 기록은 각 폰 안에만 저장되어서, 주소가 공개되어도 다른 사람 기록이 보이지 않는다
- 이전: 7단계(마지막)에 배포하려고 했다
- 비고: 아버지가 쓰시기 시작한 뒤에는 고장 난 코드를 push하면 아버지 폰에도 바로 간다. push 전에 테스트와 빌드를 돌린다. 개발자 폰은 아이폰, 아버지 폰은 갤럭시(안드로이드)라 기준은 안드로이드 크롬이고, 아이폰은 개발 중 확인용이다. 5.5단계에 어느 폰으로 보여드릴지는 아직 정하지 않았다

## 2026-10-23 PC에서도 날짜 칸을 누르면 달력이 열리게
- 결정: 마우스로 쓰는 기기(PC)에서는 투명한 날짜 칸이 눌렸어도 앱이 직접 달력을 연다(`showPicker()`). 폰(손가락)은 지금처럼 브라우저에 맡긴다
- 이유: 배포 뒤 개발자가 PC로 확인하니 날짜 상자를 눌러도 반응이 없었다. PC 크롬은 날짜 칸 오른쪽의 달력 아이콘을 눌러야만 달력을 여는데, 그 아이콘까지 투명하게 가려져 있었다. 폰은 이미 진짜 폰에서 확인했으므로 동작을 바꾸지 않았다
- 이전: 투명한 날짜 칸이 직접 눌리면 "브라우저가 이미 열었다"고 보고 아무것도 하지 않았다 (2026-10-23 "날짜 칸은 앱이 글자를 그리고…")
- 비고: PC 크롬의 폰 크기 보기(F12 기기 툴바)는 손가락 기기인 척을 해서 여전히 안 열릴 수 있다. 진짜 폰은 영향이 없어서 그대로 두었다. 고친 뒤 PC 크롬 보통 화면에서 개발자가 확인함

## 2026-10-23 PWA: 새 버전은 다음에 열 때 뜬다
- 결정: `vite-plugin-pwa`로 앱 소개 파일(manifest)과 서비스 워커를 만든다. 앱 파일을 처음 열 때 폰에 받아 두고, 그다음부터는 인터넷 없이도 열린다. 새 버전이 나오면 묻지 않고 받아 두지만 화면을 저절로 새로 고치지 않는다. 그래서 push한 뒤에는 앱을 한 번 열었다 닫고 다시 열어야 새 버전이 뜬다. 앱 이름은 "부추 하우스", 아이콘은 초록 바탕에 흰 부추 잎(`public/icon.svg`에서 PNG를 만듦)
- 이유: 아버지가 기록을 입력하는 도중에 화면이 저절로 바뀌어 입력하던 내용이 날아가면 안 된다. "새 버전이 있어요, 바꿀까요?" 같은 질문도 아버지께는 헷갈린다. 앱 이름은 이미 쓰던 탭 제목을 그대로 썼다
- 비고: PC 크롬에서 인터넷을 끊고 다시 열어 목록이 뜨는 것을 확인했고, 개발자가 아이폰에서 확인했다. 갤럭시는 아직 확인 못 함

## 2026-10-23 아버지 폰(갤럭시)과 형 폰(아이폰) 모두 지원
- 결정: 모든 기능이 갤럭시(안드로이드 크롬)와 아이폰(사파리) 두 폰에서 다 동작해야 한다. 한쪽에만 되는 기능은 쓰지 않고, 브라우저가 그리는 부분(날짜 칸, 홈 화면 추가 등)은 두 폰에서 따로 확인한다. `CLAUDE.md` "사용자"에도 적었다
- 이유: 개발자가 "형은 아이폰이고 아빠는 갤럭시라 둘 다 사용할 수 있게 해야 한다"고 정했다. 개발자 폰도 아이폰이다
- 이전: "기준은 안드로이드 크롬이고 아이폰은 개발 중 확인용"이라고 적었다 (2026-10-23 "Vercel 배포를 5단계로 앞당김"의 비고). 형이 아이폰을 쓰는 것을 반영하지 못한 것이었다

## 2026-10-23 5.5단계(아버지 시험)는 따로 하지 않고 6단계로
- 결정: 아버지께 보여드리는 자리를 따로 만들지 않는다. 아버지가 직접 써 보시고 알려주시기로 했다. 갤럭시 설치 확인도 그때 한다. 그 사이 6단계(로그인·동기화)를 먼저 진행한다
- 이유: 개발자가 "알아서 테스트해 보고 알려주실 거니까 굳이 안 해도 된다"고 정했다. 갤럭시는 지금 손에 없어서 확인할 수 없다
- 이전: 5.5단계에서 폰 한 대로 아버지께 보여드리고 30초 안에 입력되는지, 글자·버튼 크기를 직접 보려고 했다

## 2026-10-23 로그인은 이메일 + 비밀번호, 계정은 직접 만든다
- 결정: 로그인은 Supabase의 이메일 + 비밀번호로 한다. 계정은 개발자가 Supabase 화면에서 직접 만들고("Auto Confirm User"), 가입은 막는다. 앱에는 가입 화면이 없다. 지금은 개발자 계정 하나만 만들었고, 아버지·형 계정은 나중에 만든다
- 이유: Claude가 세 가지(이메일 + 비밀번호 / 메일 링크 / 카카오)를 비교해 이메일 + 비밀번호를 추천했고 개발자가 받아들였다. 메일 링크는 아이폰에서 링크를 누르면 사파리가 열려 홈 화면 앱이 로그인되지 않는다. 카카오는 카카오 개발자 등록이 필요하고 아이폰 홈 화면 앱에서 로그인 화면이 오갈 때 문제가 생기기 쉽다. 사용자가 둘뿐이라 가입 화면이 필요 없고, 가입을 막으면 모르는 사람이 계정을 만들 수 없다

## 2026-10-23 로그인할 때 시험 기록은 지운다
- 결정: 로그인 전에 넣은 기록(입력한 사람이 임시 id)은 로그인 직후 폰에서 지우고, 서버로 올리지 않는다
- 이유: Claude가 추천했고 개발자가 받아들였다. 임시 id 기록을 올리면 "누가 입력했는지"가 틀리게 남는다. 진짜 기록은 종이 영농일지에 있다. 기록은 추가만 한다는 규칙의 예외지만, 시험 기록이라 버린다
- 이전: "서버로 올릴지는 6단계에서 정한다 (확인 필요)" (2026-10-22 "로그인 전 입력한 사람은 임시 id")

## 2026-10-23 records 권한: 로그인한 사람은 모두 보고, 자기 이름으로만 추가
- 결정: Supabase `records` 테이블에 두 겹으로 권한을 둔다 (`supabase/records.sql`)
  - GRANT(표 단위): 로그인 안 한 사람(`anon`)은 아무것도 못 한다. 로그인한 사람(`authenticated`)은 조회와 추가만 한다. 추가할 때 `received_at`은 넣을 수 없다(서버 시각만)
  - RLS(줄 단위): 조회는 모든 기록, 추가는 `recorded_by`가 로그인한 본인 id일 때만. 수정·삭제 규칙은 만들지 않아 아무도 못 한다
- 이유: publishable 키는 앱 JS 파일에 들어가 누구나 볼 수 있으므로, 막는 것은 권한이 해야 한다. 아버지·형은 서로의 기록을 봐야 한다(형이 친 약도 아버지 폰에 나와야 함). 남의 이름으로 기록을 넣지 못하게 한다. 기록은 추가만 한다는 규칙을 서버에서도 지킨다. `received_at`을 폰이 정하면 폰 시계가 틀릴 때 내려받기가 기록을 놓칠 수 있다
- 비고: 로그인 없이 조회·추가·삭제를 보내 모두 `permission denied`(HTTP 401)로 막히는 것을 확인했다. 로그인한 사람의 추가·조회, 남의 이름으로 추가가 막히는지는 6-4단계(올리기)에서 확인한다

## 2026-10-23 로그인한 사람은 폰에 따로 적어 두고, 화면은 그걸로 연다
- 결정: 로그인에 성공하면 "누가 로그인했나"(사용자 id, 이메일)를 폰(localStorage)에 따로 적어 둔다. 앱을 열 때는 이 값이 있으면 바로 목록을 연다. Supabase 로그인 표(토큰)는 서버로 보낼 때만 쓴다
- 이유: Supabase 로그인 표는 1시간마다 인터넷으로 새로 받아야 한다. 이 표로 로그인 여부를 정하면 하우스에서 인터넷이 끊긴 채 앱을 열 때 로그인 화면이 떠서 기록을 못 한다. 기록 저장이 로그인 확인보다 우선이다
- 비고: 비밀번호를 바꾸거나 계정을 지워 서버가 로그인을 거절할 때 어떻게 할지는 6-4단계(올리기)에서 정한다

## 2026-10-23 가입은 열지 않는다
- 결정: 앱에 가입 화면을 만들지 않고, Supabase의 가입도 막아 둔다. 계정은 개발자가 Supabase 화면에서 만들고, 설치할 때 옆에서 첫 로그인을 해 드린다
- 이유: 개발자가 "알아서 가입하게 하면 어떨까"를 물었고, Claude가 추천하지 않는 이유를 설명해 개발자가 열지 않기로 했다. 권한 규칙이 "로그인한 사람은 모든 기록을 본다"라서, 가입을 열면 공개된 앱 주소를 아는 아무나 가입해 농장 기록을 보고 넣을 수 있다. 막으려면 "허락된 사람 명단" 표와 권한 규칙을 다시 짜야 하고, 가입 확인 메일(아이폰에서는 사파리로 열림)도 아버지께 어렵다. 사용자가 둘뿐이라 개발자가 계정을 만드는 편이 간단하다
- 비고: 다른 농가에 서비스하게 되면(사업 아이디어 B) 가입이 필요하다. 그때 농장마다 기록을 나누는 일과 함께 설계한다

- 결정: 앱 사용자는 아버지와 형뿐이다. 일하는 분들(베트남 근로자 등)은 지금 사용자가 아니다. 나중에 업무 일정·알림 기능이 생기면 대상이 될 수 있다. `CLAUDE.md` "사용자"에 적었다
- 이유: 개발자가 정했다. 업무 일정(인력 관리)과 알림(푸시 알림)은 이번 범위 밖이다
- 비고: "3명 이상 사용자·권한 관리"를 범위에서 뺀 것은 사람 수가 아니라 관리 기능(앱 안에서 가입·초대, 사람마다 다른 권한, 계정 막기)을 뜻한다. 지금 코드는 계정이 몇 개든 모두 같은 권한으로 동작한다
