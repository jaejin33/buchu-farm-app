# 브라우저 history와 뒤로 가기

앱 3단계에서 목록 ↔ 기록 입력 화면을 오갈 때 쓴 방식이다 (`src/App.tsx`). 4단계에서 이력 화면이 더해져 목록 → 기록 입력 → 이력 세 칸이 되었다. 이 프로젝트에서 어떻게 썼는지는 [[2026-10-22-3단계-코드-읽기]] 6번, [[2026-10-22-4단계-코드-읽기]] 4번에 있다.

## 1. 왜 필요한가

이 앱은 **페이지가 하나뿐**이다. 목록에서 기록 화면으로 갈 때 새 주소를 서버에 요청하지 않고, 같은 페이지 안에서 React가 그리는 내용만 바꾼다 ([[2026-10-22-React-state와-이벤트]]).

그런데 브라우저는 그걸 "페이지 이동"으로 모른다. 그래서 아무것도 안 하면:

1. 목록에서 3동을 눌러 기록 화면을 연다
2. 안드로이드 폰의 **뒤로 가기** 버튼을 누른다
3. 브라우저는 "이 페이지 전에 있던 곳"으로 간다 → **앱이 꺼진다** (홈 화면에 추가한 앱이면 앱 밖으로 나감)

아버지가 기록 화면에서 뒤로 가기를 누르면 목록으로 돌아와야 한다. 그래서 "화면을 바꿨다"는 것을 브라우저에 직접 알려 준다.

**Spring + Thymeleaf에는 이 문제가 없다.** 화면마다 주소가 달라서(`/houses` → `/houses/3/records/new`) 브라우저가 알아서 방문 기록을 쌓는다. 이 노트의 내용은 페이지 하나로 화면을 바꾸는 앱(SPA)에서만 필요하다.

## 2. 방문 기록에 쌓기: `history.pushState`

```ts
function open(next: NonNullable<Screen>) {   // next = { houseNo: 3, view: 'form' } 같은 값
  ...
  history.pushState(next, '')   // 방문 기록 한 칸 추가
  setScreen(next)               // 화면 바꾸기
}
```

- `history`는 브라우저의 **방문 기록(뒤로/앞으로 목록)**이다
- `pushState(상태, '')`: 페이지를 새로 불러오지 않고 **방문 기록에 한 칸만 추가**한다. 첫 인자는 그 칸에 붙여 두는 값이다. 여기서는 `{ houseNo: 3, view: 'form' }` (3동 기록 입력 화면)
- 둘째 인자 `''`는 예전에 쓰던 자리라 지금은 의미가 없다. 셋째 인자로 주소를 바꿀 수도 있는데(`/houses/3`), 이 앱은 주소를 바꾸지 않았다. 주소를 바꾸면 그 주소로 새로고침했을 때 서버(Vercel)에도 설정이 필요해서다

이제 방문 기록은 `[목록] → [3동 기록]` 두 칸이다. 여기서 "지난 기록"을 누르면 `{ houseNo: 3, view: 'history' }` 칸이 하나 더 쌓여 `[목록] → [3동 기록] → [3동 이력]` 세 칸이 된다.

## 3. 뒤로 가기 받기: `popstate`

```ts
useEffect(() => {
  const onPopState = (e: PopStateEvent) => setScreen(screenFromHistory(e.state))
  window.addEventListener('popstate', onPopState)
  return () => window.removeEventListener('popstate', onPopState)
}, [])
```

- 폰의 뒤로 가기를 누르면 브라우저가 방문 기록을 한 칸 뒤로 옮기고 **`popstate` 이벤트**를 보낸다
- `e.state`는 **돌아간 칸**에 붙어 있던 값이다. 이력에서 뒤로 가면 `{ houseNo: 3, view: 'form' }` → 3동 기록 화면, 한 번 더 가면 목록 칸이라 `null` → 목록 화면
- 앞으로 가기를 누르면 다음 칸으로 가서 그 화면이 다시 열린다
- `addEventListener` / `removeEventListener`: 이벤트 등록과 해제. Java Swing의 `addActionListener` / `removeActionListener`와 같다. `useEffect`의 정리 함수에서 해제한다 → [[2026-10-22-React-state와-이벤트]] 5번

### 돌아가는 길은 하나로

```ts
onCancel={() => history.back()}     // 기록 화면의 "‹ 목록" 버튼
onBack={() => history.back()}       // 이력 화면의 "‹ 3동 기록" 버튼
function handleSaved(text: string) {
  setMessage(text)
  history.back()                    // 저장 후
}
```

화면의 "‹" 버튼과 저장 후에도 `setScreen(null)`을 직접 부르지 않고 **`history.back()`**(뒤로 가기 버튼을 누른 것과 같음)을 쓴다. 그러면 폰 버튼, 화면 버튼, 저장 후 모두 `popstate` 한 곳을 거쳐 한 칸 앞 화면으로 간다.

직접 `setScreen(null)`을 쓰면 화면은 목록인데 방문 기록에는 `[3동 기록]` 칸이 남는다. 그 상태에서 뒤로 가기를 누르면 목록 → 목록이 되어 한 번 더 눌러야 하거나, 앱이 꺼지는 등 꼬인다.

### 새로고침해도 보던 화면 유지

```ts
const [screen, setScreen] = useState(() => screenFromHistory(history.state))
```

`history.state`는 **지금 칸**에 붙은 값이다. 기록 화면이나 이력 화면에서 새로고침하면 페이지는 새로 불러오지만 방문 기록 칸은 그대로라, 그 값을 읽어 같은 화면으로 다시 시작한다.

```ts
function screenFromHistory(state: unknown): Screen {
  const s = state as { houseNo?: unknown; view?: unknown } | null
  if (typeof s?.houseNo !== 'number') return null
  return { houseNo: s.houseNo, view: s.view === 'history' ? 'history' : 'form' }
}
```

`history.state`에는 아무 값이나 들어 있을 수 있어서 타입이 `unknown`(모름)이다. 동 번호가 숫자인지 확인하고, `view`가 `'history'`가 아니면 기록 화면으로 본다. Java로 치면 `Object`를 받아 `instanceof Integer`로 확인하는 것이다.

## 4. 스크롤 위치

브라우저는 뒤로 가기 때 원래 스크롤 위치를 알아서 되돌리려 한다(`history.scrollRestoration = 'auto'`). 그런데 이 앱은 `popstate`를 받은 **뒤에** React가 목록을 다시 그리므로, 브라우저가 되돌리는 순간에는 목록이 아직 없다. 그래서 위치가 틀어진다.

```ts
history.scrollRestoration = 'manual'   // 브라우저는 손대지 말 것
...
listScrollY.current = window.scrollY   // 열 때 위치를 적어 두고
...
window.scrollTo(0, screenKey === 'list' ? listScrollY.current : 0)   // 목록이 그려지면 그 자리로, 다른 화면은 맨 위
```

브라우저가 되돌리지 않게 끄고, 직접 적어 뒀다가 되돌린다. 25동을 기록하고 와도 25동 근처가 그대로 보인다 → [[2026-10-22-React-state와-이벤트]] 5번 `useLayoutEffect`, `useRef`

## 5. 라우터 라이브러리를 안 쓴 이유

React에서는 보통 `react-router` 같은 라이브러리로 이 일을 한다. 주소마다 화면을 정하고(`/houses/:no` → 기록 화면), 뒤로 가기도 알아서 처리한다. Spring의 `@GetMapping("/houses/{no}")`과 비슷한 모양이다.

이 앱은 화면이 셋(목록, 기록 입력, 이력)뿐이고 주소를 바꿀 필요도 없어서 쓰지 않았다. 패키지 하나와 배울 것 하나를 줄였다. 화면이 많아지거나, 특정 화면을 주소로 바로 열어야 하는 일이 생기면 그때 바꾼다.
