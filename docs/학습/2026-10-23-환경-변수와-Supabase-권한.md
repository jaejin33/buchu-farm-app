# 환경 변수와 Supabase 권한

6단계(Supabase 로그인·동기화) 준비에서 나온 내용이다. 앱이 Supabase에 어떻게 연결되는지, 공개된 키로 들어온 사람을 무엇이 막는지, 인터넷이 끊겨도 로그인이 풀리지 않게 한 방법을 정리한다. 이 프로젝트의 코드는 [[2026-10-23-6단계-코드-읽기]].

## 1. 환경 변수: `.env`와 `VITE_`

```
# .env (이 PC에만 있음, Git에 안 올림)
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

```ts
// 코드에서 읽기
const url = import.meta.env.VITE_SUPABASE_URL
```

- **`.env`**: 주소·키처럼 환경마다 다른 값을 코드 밖에 둔다. `.gitignore`에 있어서 Git에 안 올라간다
- **`.env.example`**: 무엇을 채워야 하는지 보여 주는 빈 견본이다. 이건 Git에 올린다. 다른 PC에서 받으면 이걸 `.env`로 복사해 채운다
- **`VITE_`로 시작해야 화면 코드에서 읽힌다.** Vite가 빌드할 때 `import.meta.env.VITE_...` 자리에 값을 그대로 박아 넣는다. 즉 **사용자 폰에 내려가는 JS 파일 안에 값이 들어간다.** 이름이 `VITE_`로 시작하지 않으면 넣어 주지 않는데, 비밀 값이 실수로 새는 것을 막는 장치다
- `import.meta.env`: Vite가 주는 값 묶음이다. Node의 `process.env`와 비슷하다

| | Spring | 우리 앱 (Vite) |
|---|---|---|
| 값 두는 곳 | `application-local.yml`, 서버 환경 변수 | `.env`, Vercel 환경 변수 |
| 읽는 법 | `@Value("${supabase.url}")` | `import.meta.env.VITE_SUPABASE_URL` |
| 값이 어디에 있나 | **서버 안**. 사용자는 못 봄 | **사용자 폰의 JS 파일 안**. 누구나 볼 수 있음 |

마지막 줄이 가장 큰 차이다. 그래서 화면 코드에는 **공개되어도 되는 값만** 넣는다.

### Vercel에도 넣는 이유

Vercel은 GitHub에서 코드를 받아 빌드한다. `.env`는 Git에 없으니 Vercel은 값을 모른다. 그래서 Vercel 화면(Settings → Environment Variables)에 같은 값을 넣는다. "Import .env" 버튼으로 `.env` 파일을 통째로 올려도 된다(공개용 값만 있을 때).

넣을 때 "Keep This Value Private. The VITE_ prefix exposes this value to the browser"라는 경고가 뜬다. "`VITE_` 값은 브라우저에 보이는데 괜찮냐"는 뜻이다. 우리 두 값은 공개용이라 **"Config"(공개해도 되는 설정)로 두면 된다.** `VITE_`를 빼면 앱이 값을 못 읽는다.

## 2. publishable 키는 공개되는 키다

| 키 | 어디에 | 공개되어도 되나 |
|---|---|---|
| Project URL | `.env`, Vercel | 됨 (주소일 뿐) |
| **Publishable key** (`sb_publishable_...`, 예전 이름 `anon` 키) | `.env`, Vercel | **됨.** 브라우저에 넣으라고 만든 키 |
| **Secret key** (`sb_secret_...`, 예전 이름 `service_role`) | **어디에도 안 넣음** | **절대 안 됨.** 모든 권한을 가진 키 |

publishable 키를 본 사람은 누구든 우리 Supabase에 요청을 보낼 수 있다. **이 키는 보안 장치가 아니다.** Spring으로 치면 API 서버 주소(`https://api.우리회사.com`)와 같다. 주소가 알려져도 괜찮은 이유는 Spring Security가 로그인과 권한을 검사하기 때문이다. 우리 앱에서 그 일은 아래 3번(GRANT + RLS)과 가입 막기가 한다.

키를 숨길 방법은 없다. 폰이 Supabase에 직접 연결하는 구조라 키가 폰에 있어야 한다. 숨기려면 중간에 우리 서버를 둬야 하는데, "별도 백엔드 서버를 쓰지 않는다"는 원칙과 맞지 않고 지금 규모에는 과하다.

## 3. 문을 두 겹으로: GRANT와 RLS

Supabase는 요청한 사람을 두 가지 **역할(role)** 중 하나로 본다.

- `anon`: 로그인 안 함 (publishable 키만 들고 온 사람)
- `authenticated`: 로그인함 (아버지, 형)

```sql
-- 1겹: GRANT (표 단위) — 이 역할이 이 표에 무엇을 할 수 있나
revoke all on public.records from anon, authenticated;     -- 먼저 다 막고
grant select on public.records to authenticated;           -- 로그인한 사람은 조회
grant insert (id, house_no, ..., recorded_at) on public.records to authenticated;  -- 추가 (received_at 빼고)

-- 2겹: RLS (줄 단위) — 그중 어떤 줄(기록)에 할 수 있나
alter table public.records enable row level security;
create policy "로그인한 사람은 모든 기록 조회" on public.records for select to authenticated using (true);
create policy "자기 이름으로만 기록 추가" on public.records for insert to authenticated
  with check (recorded_by = (select auth.uid()));
```

| 겹 | 비유 | Spring에서는 |
|---|---|---|
| GRANT | 건물 출입 권한 | `@PreAuthorize("isAuthenticated()")` |
| RLS | 들어간 뒤 열 수 있는 방 | 서비스 코드의 `if (!r.getRecordedBy().equals(me)) throw new AccessDeniedException(...)` |

- **DB가 직접 검사한다.** Spring에서는 서버 코드가 검사하고 DB는 서버를 믿는다. 우리는 중간 서버가 없어서 폰이 DB에 바로 요청하므로, DB가 검사해야 한다
- `using (...)`: 조회할 때 보이는 줄의 조건. `true`면 모든 줄이다
- `with check (...)`: 추가할 때 들어가도 되는 줄의 조건
- `auth.uid()`: Supabase가 주는 함수로, 지금 로그인한 사람의 id다. `(select auth.uid())`처럼 괄호로 감싸면 요청마다 한 번만 계산해서 빠르다
- **허락하는 규칙이 없으면 막힌다.** RLS를 켜면 기본이 "모두 막음"이다. 수정(update)·삭제(delete) 규칙을 안 만들었으니 아무도 못 한다. 기록은 추가만 한다는 규칙을 서버에서도 지키는 셈이다 → [[2026-10-22-추가만-하는-기록과-취소]]
- `grant insert (열 목록)`: 열 단위로도 막을 수 있다. `received_at`을 빼서 폰이 이 값을 정하지 못하고, 항상 서버 시각(`default now()`)이 들어간다
- GRANT가 먼저 검사된다. GRANT에서 막히면 RLS까지 가지도 않고 `permission denied`가 난다

Supabase 화면의 "This table can be accessed via the Data API"는 "이 표는 인터넷 요청 창구(Data API)로 열려 있다"는 뜻이다. 앱이 그 창구로 기록을 주고받으므로 열려 있어야 하고, 누가 무엇을 하는지는 위 두 겹이 정한다.

### 정말 막히는지 확인하기

publishable 키만 들고 직접 요청을 보내 봤다(키는 `.env`에서 읽고 화면에 찍지 않음).

```bash
curl "$URL/rest/v1/records?select=id" -H "apikey: $KEY"
# → {"code":"42501","message":"permission denied for table records"}  (HTTP 401)
```

조회·추가·삭제 모두 이렇게 막혔다. 응답의 `hint`는 "anon에게 권한을 주면 된다"고 알려 주지만, 우리는 일부러 막은 것이라 따르지 않는다. Spring으로 치면 Postman으로 로그인 없이 API를 불러 401이 나는지 보는 것과 같다.

## 4. 로그인 표(토큰)와 오프라인

로그인하면 Supabase가 표 두 장을 준다.

| 표 | 수명 | 하는 일 |
|---|---|---|
| access token | 1시간 | 요청마다 "나 로그인했어"를 증명한다 |
| refresh token | 길다 | access token이 지나면 인터넷으로 새 access token을 받는다 |

`supabase-js`가 이 둘을 폰(localStorage)에 두고, 인터넷이 될 때 알아서 새로 받는다(`autoRefreshToken`).

문제는 **하우스에서 인터넷이 끊긴 채 앱을 열 때**다. 마지막으로 연 지 1시간이 지났으면 access token이 지나 있고, 새로 받을 수도 없다. 이 표만 보고 "로그인했나"를 정하면 로그인 화면이 뜨고, 로그인도 인터넷이 필요하니 **기록을 아예 못 한다.**

그래서 로그인에 성공하면 "누가 로그인했나"(id, 이메일)를 **따로** 폰에 적어 두고, 앱은 그 값을 보고 목록을 연다. 표는 서버로 보낼 때(6-4단계)만 쓰고, 그때 인터넷이 되면 새로 받는다 → [[결정기록]] "로그인한 사람은 폰에 따로 적어 두고, 화면은 그걸로 연다"

Spring의 세션은 보통 반대다. 세션이 만료되면 로그인 페이지로 보낸다. 서버와 늘 연결된 웹이라 가능한 방식이다. 우리 앱은 **기록 저장이 로그인 확인보다 우선**이다.

### localStorage

브라우저가 주는 아주 작은 저장소다. 글자(문자열)만 이름표(key)로 저장한다.

```ts
localStorage.setItem('buchu-farm:user', JSON.stringify({ id: '...', email: '...' }))  // 저장 (객체 → 글자)
JSON.parse(localStorage.getItem('buchu-farm:user'))                                   // 읽기 (글자 → 객체)
```

- 바로(동기로) 읽혀서 앱을 열자마자 쓸 수 있다. IndexedDB는 `await`가 필요하다
- 기록처럼 많은 것은 IndexedDB에, "누가 로그인했나" 같은 작은 값 하나는 localStorage에 둔다
- `JSON.stringify`/`JSON.parse`: 객체 ↔ JSON 글자. Java의 Jackson `writeValueAsString` / `readValue`
- 주소마다 따로이고, 아이폰은 사파리와 홈 화면 앱도 따로다 (IndexedDB와 같음, [[2026-10-22-IndexedDB와-Dexie]] 2번)

## 5. 가입 막기와 계정 만들기

- Supabase → Authentication → Sign In / Providers → **"Allow new users to sign up" 끔.** 앱 밖에서 누가 가입 요청을 보내도 계정이 안 생긴다. 공개된 키로 할 수 있는 가장 위험한 일(가입해서 `authenticated` 되기)을 막는다
- 계정은 Authentication → Users → Add user → Create new user. **"Auto Confirm User"** 체크로 확인 메일 없이 바로 쓴다
- 비밀번호는 길게(12자 이상). Supabase도 로그인 시도 횟수를 제한한다

### 가입을 열지 않는 이유

권한 규칙이 "로그인한 사람은 모든 기록을 본다"(`using (true)`)라서, **가입을 막아 둔 것이 가장 중요한 문**이다.

```
가입을 열면: 앱 주소를 아는 아무나 → 가입 → authenticated → 농장 기록 전부 조회·추가
```

가입을 열면서 안전하려면 "허락된 사람 명단" 표를 두고 RLS를 "로그인했고 명단에 있는 사람만"으로 바꿔야 한다. 결국 개발자가 명단에 사람을 넣어야 해서, 계정을 직접 만드는 것과 손이 비슷하다. 그래서 열지 않았다 → [[결정기록]] "가입은 열지 않는다"

### "사용자·권한 관리"란

지금 코드는 계정이 몇 개든 모두 같은 권한으로 동작한다. 범위에서 뺀 "사용자·권한 관리"는 사람 수가 아니라 **사람이 늘면 필요해지는 기능**이다.

| | 지금 | 사용자·권한 관리가 있는 앱 |
|---|---|---|
| 계정 | 개발자가 Supabase 화면에서 | 앱 안에서 초대·가입·탈퇴 |
| 권한 | 모두 같음 | 사람마다 다름 (예: 입력만 / 전체 보기·취소) |
| 사람이 나가면 | 생각 안 함 | 계정 막기, 그 사람 기록 처리 |

Spring으로 치면 지금은 `isAuthenticated()` 하나로 끝나는 앱이고, 권한 관리는 `ROLE_ADMIN`·`ROLE_WORKER`를 나누고 관리 화면에서 역할을 주고 빼는 것이다. 일하는 분들은 지금 사용자가 아니다 → [[결정기록]] "일하는 분들은 지금 사용자가 아니다"

## 6. 무료 요금제에서 알아둘 것 (2026년 10월 확인)

| | Vercel Hobby | Supabase Free |
|---|---|---|
| 값 | 무료 (카드 없으면 청구 없음) | 무료 |
| 한도 | 전송 100GB/월, 요청 100만/월, 배포 100회/일 | 프로젝트 2개, DB 500MB |
| 한도를 넘으면 | 청구 없이 최대 30일 멈춤 | - |
| 조심할 것 | **개인·비상업 용도만.** 다른 농가에 서비스하면 Pro(월 $20) | **7일 동안 안 쓰면 프로젝트가 멈춤.** 화면에서 다시 켜면 됨. **자동 백업 없음** |

- 우리 앱은 0.5MB 정도라 Vercel 한도를 넘을 일이 거의 없다. 기록은 한 줄에 몇백 바이트라 500MB도 넉넉하다
- 여름처럼 안 쓰는 철에는 Supabase가 멈출 수 있다. 멈춰도 앱은 폰 안 기록으로 동작하고, 다시 켜면 동기화가 이어진다
