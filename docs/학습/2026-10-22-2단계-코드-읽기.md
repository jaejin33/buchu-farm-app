## 1. 파일 지도

```
src/
├ main.tsx                 시작점. App을 화면에 붙인다 (Vite 템플릿 그대로)
├ App.tsx                  [바뀜] 데이터를 모아 HouseList에 넘긴다
├ index.css                [바뀜] 앱 전체 색과 기준 글자 크기
├ config/houses.ts         [새로] 25동 설정
├ data/fakeRecords.ts      [새로] 가짜 기록 (3단계에서 지움)
├ domain/
│  ├ types.ts              [바뀜] House 타입 추가
│  ├ harvestCalc.ts        [바뀜] harvestableDate 추가
│  └ today.ts              [새로] 한국 시간 "오늘"
└ pages/
   ├ HouseList.tsx         [새로] 하우스 목록 화면
   └ HouseList.css         [새로] 그 화면의 모양
```

누가 누구를 부르는지:

```
main.tsx
  └→ App.tsx
       ├→ config/houses.ts      HOUSES (25동)
       ├→ domain/today.ts       todayInKorea()  → "2026-10-22"
       ├→ data/fakeRecords.ts   makeFakeRecords(today)  → 가짜 기록 배열
       └→ pages/HouseList.tsx   위 세 가지를 props로 받음
              └→ domain/harvestCalc.ts   getHouseStatus, harvestableDate
```

**계층 규칙이 지켜지는지 보기:** `HouseList.tsx`는 `domain/`(계산)만 부른다. `data/`나 `config/`는 모른다. 데이터를 모으는 일은 `App.tsx`가 한다. Spring으로 치면 `App.tsx`가 컨트롤러, `HouseList.tsx`가 뷰 템플릿, `domain/`이 도메인 로직이다.

삭제한 것: `App.css`, `src/assets/` 이미지 3개, `public/icons.svg`. Vite 프로젝트를 만들 때 딸려 온 예시 화면용 파일이다.

## 2. `types.ts`: `House` 타입 추가

```ts
export type HouseProblem =
  | 'drainage' // 💧 배수가 안 됨
  | 'mycelium' // 🍄 버섯균사가 많음

export interface House {
  no: number
  zone: string
  crop: string
  problems: HouseProblem[]
}
```

- **문제 상태는 "있다/없다"만 둔다.** 정도를 숫자로 두지 않았다 → [[결정기록]] "하우스 문제 상태는 있다/없다만"
- `problems`를 `drainage: boolean`, `mycelium: boolean` 두 필드가 아니라 **배열**로 했다. 문제 종류가 늘어나도 `HouseProblem`에 하나만 추가하면 되고, 화면은 배열을 돌며 아이콘을 그리기만 하면 된다. 문제가 없으면 빈 배열 `[]`이다
- `crop`(작물)은 지금 모두 `'부추'`지만 넣어 두었다. 형이 다른 작물도 생각하고 있어서다 ([[진행기록]] 4번)

## 3. `config/houses.ts`: 25동 설정

```ts
export const HOUSES: readonly House[] = [
  { no: 1, zone: '1구역', crop: '부추', problems: [] },
  { no: 3, zone: '1구역', crop: '부추', problems: ['drainage'] },
  ...
]
```

- **그냥 데이터 목록이다.** 함수도 계산도 없다. Spring의 `application.yml`에 목록을 적어 두고 `@ConfigurationProperties`로 읽는 것과 목적이 같다. 다만 여기서는 TS 파일이라 `House` 타입 검사를 받는다. `zone`을 빼먹거나 `'drainag'`처럼 오타를 내면 빌드 에러가 난다
- `HOUSES`처럼 대문자로 쓴 건 "바뀌지 않는 상수"라는 관례다 (Java의 `static final` 이름 짓기와 같음)
- **적힌 순서가 의미가 있다.** 화면의 구역 순서가 이 파일에 처음 나온 순서를 따른다
- 구역 6개는 실제 값이다. **문제 상태는 아직 가짜**라서 파일 맨 위에 적어 두었다

## 4. `domain/today.ts`: 한국 시간 "오늘"

```ts
const KST_OFFSET_MS = 9 * 60 * 60 * 1000

export function todayInKorea(now: Date = new Date()): string {
  return new Date(now.getTime() + KST_OFFSET_MS).toISOString().slice(0, 10)
}
```

한 줄짜리지만 원리가 있다.

1. `now.getTime()`: 1970-01-01 00:00 UTC부터 지난 밀리초. **세계 어디서나 같은 숫자**다 (Java의 `Instant.toEpochMilli()`)
2. 여기에 9시간을 더한다
3. `.toISOString()`은 항상 **UTC 기준**으로 `"2026-10-22T00:30:00.000Z"` 같은 글자를 만든다. 9시간을 미리 더했으니 이 글자가 곧 한국 시각이다
4. `.slice(0, 10)`: 앞 10글자 `"2026-10-22"`만 자른다 (Java의 `substring(0, 10)`)

예: UTC `2026-10-21 15:00` + 9시간 = `2026-10-22 00:00` → `"2026-10-22"`. 한국 자정에 날짜가 바뀐다. 테스트(`today.test.ts`)가 이 경계를 지킨다.

Java로는 `LocalDate.now(ZoneId.of("Asia/Seoul")).toString()` 한 줄이다. JS에는 시간대를 지정해 날짜만 꺼내는 쉬운 기본 기능이 없어서 이렇게 했다.

**왜 따로 파일을 만들었나:** `harvestCalc.ts`는 "오늘"을 인자로 받고 현재 시각을 직접 읽지 않는다 ([[2026-10-22-Vitest-테스트와-순수-함수]] 1번). 그러면 누군가는 현재 시각을 읽어야 한다. 그 일을 **이 파일 한 곳에만** 모았다. 현재 시각을 읽는 곳이 여기저기 흩어지면, 화면 일부는 어제 날짜, 일부는 오늘 날짜로 계산되는 일이 생길 수 있다.

`now: Date = new Date()`는 기본값이 있는 인자다. 앱에서는 `todayInKorea()`처럼 비워서 부르면 현재 시각을 쓰고, 테스트에서는 `todayInKorea(new Date('2026-10-21T15:00:00Z'))`처럼 시각을 넣어 고정한다. Spring에서 `Clock`을 주입하는 것과 같은 생각이다.

## 5. `domain/harvestCalc.ts`: `harvestableDate` 추가

```ts
export function harvestableDate(status: HouseStatus): string | null {
  const { sprayClearDate: clear, nextHarvestDate: next } = status
  if (next === null) return null
  if (clear !== null && clear > next) return clear
  return next
}
```

화면을 **"벨 수 있는 날이 가까운 순"으로 정렬**하려면 동마다 날짜 하나가 필요하다. 그래서 두 날짜 중 늦은 날을 고른다.

- `const { sprayClearDate: clear, nextHarvestDate: next } = status`: 구조 분해에 **이름 바꾸기**를 더한 문법이다. `status.sprayClearDate`를 꺼내 `clear`라는 이름으로 쓴다. Java로는 `String clear = status.sprayClearDate();` 두 줄과 같다
- 이미 지난 날짜일 수도 있다(🟢 수확 가능). 그래도 정렬에는 문제가 없다. 오래 기다린 동일수록 날짜가 이르니 앞에 온다

| 약 때문에 벨 수 있는 날 | 다음 수확 예정일 | 결과 |
|---|---|---|
| 없음 | 10-26 | 10-26 |
| 10-25 | 10-26 | 10-26 (수확 예정일이 늦음) |
| 10-30 | 10-26 | 10-30 (약이 늦게 풀림) |
| 10-30 | 없음 (수확 기록 없음) | **null** → 목록 맨 뒤 |

마지막 줄이 중요하다. 수확 기록이 없으면 언제 벨 수 있을지 모르니 날짜를 만들어 내지 않는다. 1단계에서 정한 "⚪ 기록 없음" 규칙과 같은 생각이다.

**왜 화면이 아니라 여기에 두었나:** 순수 계산이라 테스트하기 쉽고(5개 추가), 수확 가능일과 관련된 계산은 이 파일에 모으기로 했기 때문이다 (`CLAUDE.md`).

## 6. `data/fakeRecords.ts`: 가짜 기록

3단계에서 IndexedDB를 붙이면 지울 파일이다. 그래도 읽을 거리가 있다.

### 왜 날짜를 "며칠 전"으로 만드나

`harvest(1, '2026-09-17')`처럼 날짜를 고정해 두면, 시간이 지나 다음 달에 열었을 때 모든 동이 🟢가 된다. 그래서 **오늘을 받아서 "오늘로부터 며칠 전"으로** 만든다. 언제 열어도 네 가지 상태가 골고루 보인다.

```ts
harvest(1, 40), // 40일 전 수확 → 35일 주기가 지났으니 🟢
harvest(3, 33), // 33일 전 수확 → 2일 남음 🟡 D-2
harvest(6, 38), spray(6, 2, 7), // 이틀 전 약(수확 전 7일) → 5일 남음 🔴 D-5
```

각 줄 오른쪽 주석이 화면에 나와야 할 상태다. 화면을 보고 주석과 다르면 어딘가 잘못된 것이다.

### 함수 안의 함수 (클로저)

```ts
export function makeFakeRecords(today: string): FarmRecord[] {
  let seq = 0

  function base(houseNo: number, daysAgo: number) {
    seq += 1
    const work_date = addDays(today, -daysAgo)
    return { id: `fake-${seq}`, house_no: houseNo, work_date, ... }
  }

  const harvest = (houseNo: number, daysAgo: number): FarmRecord => ({
    ...base(houseNo, daysAgo),
    type: 'harvest',
    amount: null,
    amount_unit: null,
  })
  ...
}
```

- `base`, `harvest`, `spray` 같은 도우미 함수가 `makeFakeRecords` **안에** 있다. 그래서 바깥 함수의 `today`와 `seq`를 인자로 받지 않고 바로 쓴다. 이것을 **클로저**라고 한다
- `seq`는 기록을 하나 만들 때마다 1씩 늘어서 `fake-1`, `fake-2`... id가 겹치지 않게 한다
- **Java와 다른 점:** Java 람다는 바깥 지역 변수를 바꿀 수 없다(`effectively final`이어야 함). 그래서 Java로 쓰면 `AtomicInteger seq`를 쓰거나 클래스를 하나 만들어 필드로 둬야 한다. JS는 그냥 바꿀 수 있다

  ```java
  // Java로 쓴다면
  class FakeRecordFactory {
    private final String today;
    private int seq = 0;
    FakeRecordFactory(String today) { this.today = today; }
    HarvestRecord harvest(int houseNo, int daysAgo) { seq++; ... }
  }
  ```

- `=> ({ ... })`: 화살표 함수가 **객체를 바로 돌려줄 때는 괄호로 감싼다.** 괄호가 없으면 `{`를 함수 몸통의 시작으로 읽어 버린다
- `...base(houseNo, daysAgo)`: 공통 항목(id, 날짜, 입력자 등)을 펼쳐 넣고, 그 뒤에 종류별 항목을 덧붙인다. Vitest 노트의 테스트 도우미와 같은 방식이다
- `seq % 2 === 0 ? 'fake-father' : 'fake-brother'`: 삼항 연산자(Java와 같음). 입력자를 번갈아 넣는다. 4단계 이력 화면에서 쓸 값이다

### 취소 기록 예

```ts
const wrongHarvest = harvest(12, 3)
...
harvest(12, 37), wrongHarvest, cancel(12, wrongHarvest),
```

12번 동은 3일 전 수확을 잘못 입력했다가 취소한 상황이다. 취소가 제대로 되면 37일 전 수확을 기준으로 🟢가 뜬다. 취소가 안 되면 🟡 D-32가 뜬다. 화면에서 취소 처리를 눈으로 확인하는 용도다.

### id가 UUID가 아닌 이유

원래 규칙은 `crypto.randomUUID()`로 만든 UUID다. 그런데 이 기능은 폰에서 PC 개발 서버(`http://192.168...`)로 접속하면 막힌다. 가짜 데이터라 `fake-1`로 충분하다 → [[2026-10-22-Vite-개발-서버와-화면-확인]] 4번

## 8. `pages/HouseList.tsx`: 화면

문법은 [[2026-10-22-React-컴포넌트와-props]] 3번에서 거의 한 줄씩 설명했다. 여기서는 **순서**만 본다.

```
1. rows 만들기   동마다 { house, status, date } 계산
                 status = getHouseStatus(...)   🔴🟡🟢⚪와 D-n
                 date   = harvestableDate(status)  정렬용 날짜
2. 정렬         date가 이른 순, null은 뒤, 같으면 동 번호 순
3. zones 만들기  houses.ts에 나온 순서대로 구역 이름 목록
4. 그리기        구역마다 → 그 구역의 rows만 골라서(filter) → 카드
```

- **25동 전체를 먼저 정렬한 뒤 구역별로 나눈다.** 정렬된 배열에서 `filter`로 고르면 순서가 그대로 유지되므로, 구역 안에서도 정렬된 순서가 된다. 구역마다 따로 정렬할 필요가 없다
- 계산(`getHouseStatus`)은 1단계 코드를 그대로 부른다. 화면은 계산 방법을 모른다
- `formatToday`: `"2026-10-22"` → `"10월 22일 (목)"`. 요일은 `new Date('2026-10-22T00:00:00Z').getUTCDay()`로 구한다 (0이 일요일). UTC로 읽어야 폰 시간대 때문에 요일이 하루 밀리지 않는다
- 화면 문구 "농약 포장 표기가 우선입니다"가 여기 있다 (`CLAUDE.md`)

### 카드 한 장의 구조

```
<li class="house-card status-spray_wait">   ← 상태에 따라 색이 바뀌는 클래스
  <div class="house-top">
    <div class="house-no">7<span>동</span></div>
    <div class="house-problems">💧🍄</div>  ← 문제가 있을 때만
  </div>
  <div class="house-status">🔴 약 대기</div>
  <div class="house-dday">D-13</div>         ← 🔴🟡일 때만
</li>
```

- 💧🍄는 `role="img"`와 `aria-label="배수 문제"`를 붙였다. 화면 읽기 기능(시각 장애인용)에서 이모지 이름 대신 뜻을 읽어 주고, PC에서 마우스를 올리면 `title`로 뜻이 보인다
- 처음에는 💧🍄를 카드 오른쪽 위에 겹쳐 띄웠는데(`position: absolute`), 좁은 폰에서 "7동" 글자를 덮었다. 그래서 번호 옆에 나란히 두고, 자리가 모자라면 아래 줄로 내려가게 바꿨다(`.house-top`의 `flex-wrap: wrap`)

## 9. `HouseList.css`, `index.css`: 모양

크기 단위는 [[2026-10-22-CSS-rem-단위]]에 있다. 여기서는 색만 본다.

```css
/* index.css: 색은 이름을 붙여 한 곳에 모은다 */
:root {
  --red: #d32f2f;
  --red-bg: #fdecec;
  ...
}

/* HouseList.css: 이름으로 가져다 쓴다 */
.status-spray_wait {
  border-left-color: var(--red);
  background: var(--red-bg);
}
```

- `--red`처럼 `--`로 시작하는 것은 **CSS 변수**다. `var(--red)`로 꺼내 쓴다. Java의 상수 클래스(`Colors.RED`)와 같다. 빨간색을 바꾸려면 `index.css` 한 곳만 고치면 된다
- 카드 왼쪽 굵은 띠(6px)와 옅은 배경으로 상태를 보여주고, **글자 라벨도 함께** 둔다. 햇빛 아래에서나 색약이면 색만으로는 구분이 어렵기 때문이다
- 밝은 화면 하나만 쓴다(`color-scheme: light`). 폰이 다크 모드여도 밝게 나온다

## 10. 테스트 (42개 = 1단계 35 + 2단계 7)

| 파일 | 추가 | 지키는 것 |
|---|---|---|
| `harvestCalc.test.ts` | `harvestableDate` 5개 | 5번 표의 네 경우 + 🟢일 때 지난 날짜가 나오는지 |
| `today.test.ts` | 2개 | 한국 자정(UTC 15시)에 날짜가 바뀌는지 |

화면(`HouseList.tsx`) 자체는 테스트가 없다. 화면 테스트에는 도구(Testing Library 등)를 더 설치해야 하고, 지금 화면은 계산 결과를 그리기만 하기 때문이다. 대신 캡처한 화면을 보고 6번의 주석과 맞는지 확인했다.

## 11. 이걸 바꾸려면 어디를 고치나

| 바꿀 것 | 고칠 곳 |
|---|---|
| 구역 이름, 문제 있는 동 | `config/houses.ts` |
| 화면 전체 크기 | `index.css`의 `font: 16px/1.4 ...`에서 `16px` |
| 상태 색 | `index.css`의 `--red`, `--yellow`, `--green`, `--gray` |
| 상태 이름 ("약 대기" 등) | `HouseList.tsx`의 `STATUS_LABEL` |
| 문제 아이콘·이름 | `HouseList.tsx`의 `PROBLEM_ICON` |
| 문제 종류 추가 | `types.ts`의 `HouseProblem` + `HouseList.tsx`의 `PROBLEM_ICON` (빠뜨리면 빌드 에러) |
| 정렬 규칙 | `HouseList.tsx`의 `rows.sort(...)`, 날짜 기준은 `harvestCalc.ts`의 `harvestableDate` |
| 화면에서 보이는 가짜 상황 | `data/fakeRecords.ts`의 목록 |
