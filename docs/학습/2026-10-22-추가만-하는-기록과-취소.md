# 추가만 하는 기록과 취소

이 앱의 기록은 **고치거나 지우지 않고 추가만 한다.** 잘못 입력한 기록은 "그 기록은 없던 걸로 해 줘"라는 **취소 기록(`cancel`)**을 하나 더 추가해서 없앤다 (`CLAUDE.md` 데이터 규칙). 4단계를 시작하기 전에 "취소 기록을 입력하는 게 뭐야?"라고 물어서 설명한 내용이다.

- 계산 코드에서 취소를 거르는 법 → [[2026-10-22-1단계-코드-읽기]] 3-1번 `activeRecords`
- 화면에서 취소하는 버튼 → [[2026-10-22-4단계-코드-읽기]]
- 화면에서 수정하는 버튼 (10단계) → 6번, [[2026-10-22-3단계-코드-읽기]] 16번
- 정한 경위 → [[결정기록]] "기록은 추가만 하고 수정·삭제하지 않는다"

## 1. 예: 5동에 약을 쳤는데 3동을 눌렀다

**보통 앱이라면** 그 기록을 지우거나 고친다.

**이 앱은** 이렇게 기록이 쌓인다.

| 기록 | 종류 | 내용 |
|---|---|---|
| ① | 약 | 3동, 10월 22일 ← 실수 |
| ② | **취소** | "①을 취소함" (`target_id` = ①의 id) |
| ③ | 약 | 5동, 10월 22일 ← 제대로 다시 입력 |

화면과 계산은 ②를 보고 ①을 없는 것으로 친다. 3동의 "약 후 N일"은 원래대로 돌아가고 5동은 "오늘 약"이 된다. **"수정"도 같은 방식**이다. 취소 하나 + 새 기록 하나. 10단계부터는 이력의 [수정] 버튼이 이 둘을 한 번에 넣어 준다 (6번).

## 2. 왜 이렇게 하나: 두 폰이 서로 부딪히지 않게

6단계부터 아버지 폰과 형 폰이 각자 입력한 기록을 서버(Supabase)에 모은다. 비닐하우스 안에서는 인터넷이 끊기니, 한동안 각자 따로 기록하다가 나중에 합치게 된다.

고치기·지우기를 허락하면 이런 일이 생길 수 있다.

- 아버지 폰에서 ①을 지웠는데, 인터넷이 끊긴 형 폰에는 ①이 남아 있다가 나중에 서버로 다시 올라온다. 지운 기록이 되살아난다
- 두 사람이 같은 기록을 동시에 다르게 고친다. 어느 쪽이 맞는지 정해야 한다

**추가만 하면** 두 폰의 기록을 합치기만 하면 된다. 같은 id면 같은 기록이니 하나만 두고, 다른 id면 둘 다 넣는다. 순서가 어떻든 결과가 같다. 고칠 일이 없으니 부딪힐 일도 없다.

덤으로 **무엇을 잘못 넣고 언제 취소했는지가 남는다.** 종이 영농일지에 줄을 긋고 옆에 다시 쓰는 것과 같다. 줄 그은 글씨도 읽을 수 있다.

### 아버지와 형이 각자 계정으로 입력할 때

"각자 수정해도 괜찮나?"라는 질문에서 정리한 것이다 (10월 23일). 기록을 바꾸는 일이 없고 고칠 때도 기록을 추가하므로, 두 계정이 동시에 손대도 덮어쓸 것이 없다. 10단계의 [수정] 버튼도 속으로는 기록을 추가한다.

| 상황 | 결과 |
|---|---|
| 둘 다 인터넷이 끊긴 채 각자 입력 | id(UUID)가 다 달라서 나중에 둘 다 그대로 올라간다 |
| 같은 기록을 두 사람이 각각 취소 | 취소 기록이 2개 생길 뿐, 결과는 똑같이 "취소됨" |
| 형이 잘못 적은 것을 아버지가 고침 | 아버지 이름으로 취소 기록 + 새 기록이 들어간다 |
| 같은 날 3동 약을 아버지도 적고 형도 적음 | 기록이 2개. 계산은 마지막 하나만 쓰니 "약 후 N일"은 같다. 이력에 두 줄 보인다 |
| 같은 기록을 두 사람이 인터넷 없이 각각 [수정] (10단계) | 취소 2개 + 새 기록 2개. 원래 기록은 취소되고, 새 기록 둘이 다 남아 이력에 두 줄 보인다. 하나를 취소하면 된다. 한쪽이 사라지지는 않는다 |

지금 권한(`supabase/records.sql`)으로 할 수 있는 것은 이렇다.

- **보기:** 서로의 기록을 다 본다
- **추가:** 자기 이름(`recorded_by`)으로만 한다. 아버지 계정으로 "형이 입력함" 기록은 못 만든다
- **취소:** 남이 입력한 기록도 취소할 수 있다. 취소 기록은 취소한 사람 이름으로 남는다. 이렇게 둘지는 따로 정한 적이 없다 (확인 필요). Claude는 아버지가 형의 실수를 고쳐 주실 수 있어 편하다고 봤다

서로의 기록이 보이는 데는 시간이 걸린다. 형 폰에서 올리고(6-4), 아버지 폰이 내려받아야(6-5) 보인다. 둘 중 한 폰이라도 인터넷이 끊겨 있으면 그만큼 늦다.

## 3. 규칙

| 규칙 | 이유 |
|---|---|
| 취소 기록은 `target_id`에 취소할 기록의 id를 넣는다 | 무엇을 취소하는지 가리키기 위해 |
| **취소 기록은 취소할 수 없다** (취소를 가리키는 취소는 무시) | "취소의 취소의 취소"처럼 꼬이지 않게. 잘못 취소했으면 원래 기록을 다시 입력한다 |
| 없는 기록을 가리키는 취소는 무시한다 | 상대 폰의 기록이 아직 안 내려왔을 수도 있다. 나중에 내려오면 그때 취소된다 |
| 같은 기록을 두 번 취소해도 문제없다 | 두 사람이 동시에 취소해도 결과가 같다 |
| 수확 완료를 취소하면 그 수확량도 무시한다 | 수확량은 수확 완료 기록에 붙어 있기 때문이다 |
| 화면에서는 취소된 기록과 취소 기록을 숨긴다 | 아버지가 보기에는 "지워진 것"처럼 보이면 된다 |

계산할 때는 항상 **"살아 있는 기록"만 먼저 골라낸 뒤** 쓴다 (`harvestCalc.ts`의 `activeRecords`). 이 함수를 빠뜨리면 취소한 기록이 계산에 들어가므로, 계산 함수들은 모두 이 함수를 거친다.

## 4. Spring·Java에서 비슷한 것

**회계의 역분개**가 가장 비슷하다. 장부에 잘못 적은 줄을 지우지 않고, 반대 금액의 줄을 추가해 상쇄한다.

**DB에서 흔히 쓰는 "소프트 삭제"와는 다르다.**

```java
// 소프트 삭제: 행을 지우지 않지만, 그 행을 고친다 (UPDATE)
@Entity
class FarmRecordEntity {
    @Id UUID id;
    boolean deleted;          // 지우면 true로 바꿈
}
record.setDeleted(true);      // → UPDATE records SET deleted = true WHERE id = ?
```

```java
// 이 앱: 원래 행은 그대로 두고, 새 행을 추가한다 (INSERT만)
repository.save(new CancelRecord(UUID.randomUUID(), houseNo, today, targetId));
// → INSERT INTO records (id, type, target_id, ...) VALUES (?, 'cancel', ?, ...)
```

소프트 삭제는 결국 **같은 행을 두 폰이 고치는 것**이라, 오프라인에서 따로 고치면 부딪힌다. 이 앱은 INSERT만 하므로 부딪히지 않는다.

| | 소프트 삭제 | 이 앱 (추가만) |
|---|---|---|
| DB 작업 | `UPDATE ... SET deleted = true` | `INSERT` 취소 기록 |
| 원래 행 | 바뀜 | 그대로 |
| 두 폰이 오프라인에서 따로 작업 | 부딪힐 수 있음 | 합치기만 하면 됨 |
| 누가 언제 취소했는지 | 따로 남겨야 함 | 취소 기록 자체에 남음 (`recorded_by`, `recorded_at`) |

더 큰 이름으로는 **이벤트 소싱(event sourcing)**이라고 부르는 설계와 같은 생각이다. "지금 상태"를 저장하지 않고 "일어난 일"을 차례로 쌓은 뒤, 상태는 그때그때 계산한다. Spring 쪽에서는 Axon Framework 같은 도구가 이 방식을 쓴다. 이 앱은 도구 없이 아주 작게 쓴 셈이다: 상태(수확 후 며칠, 수확 가능)는 저장하지 않고 기록에서 매번 계산한다.

## 5. 단점

- **기록이 계속 쌓인다.** 취소한 기록도 남는다. 이 앱은 기록이 많지 않아서(하루 몇십 건) 문제가 안 된다. 한 줄이 수백 바이트라 Supabase 무료 DB(500MB)에 한참 남는다
  - 시험하면서 쌓인 기록은 양이 아니라 **아버지 화면에 섞이는 것**이 문제다. 2026-10-26 실제로 쓰기 시작하면서 서버 기록을 모두 지웠다 → [[결정기록]] "10월 26일부터 앱에 진짜 기록을 남긴다". 그 뒤로 시험한 기록은 저장해 본 즉시 취소한다 → [[결정기록]] "실제로 쓰는 중에도 시험은 진짜 Supabase에서 하고…"
- **서버에서 지운 것이 폰에서는 안 지워진다.** 지우기가 없는 설계라서, 내려받기도 "폰에 없는 것 추가"만 한다. 서버에서 `delete`로 지워도(관리자만 할 수 있음) 이미 내려간 폰에는 남는다. 폰도 비우려면 그 폰의 앱 저장 데이터를 지우고 다시 받아야 한다. 평소에 없애고 싶은 기록은 지우지 말고 취소한다. 취소는 기록 추가라 모든 폰에 전해진다
  - **취소한 뒤 서버에서 지우는 것도 위험하다.** 시험 기록과 그 취소 기록을 함께 지웠는데, 어떤 폰이 시험 기록은 받고 취소 기록은 아직 못 받았다면(그사이 앱을 안 열었음) 그 폰은 취소 기록을 영영 못 받는다. 시험 기록만 남아 계속 보인다. 폰이 무엇을 받았는지는 서버에서 알 수 없다 (2026-10-26 설명)
    ```
    개발자: 5동 약 저장 → 아버지 폰이 받음
    개발자: 취소 → 아버지 폰이 아직 못 받음
    SQL: 개발자 기록 삭제 (약 + 취소 둘 다 서버에서 없어짐)
    → 아버지 폰: "5동 약"만 남고 계속 보임
    ```
  - Spring으로 치면 여러 서버가 각자 캐시를 들고 있는데 DB 행만 지우고 "지웠다"는 이벤트는 보내지 않은 것과 같다. 캐시는 모른 채 옛 값을 계속 보여 준다. 취소 기록이 그 "이벤트" 역할을 한다
- **항상 거르고 써야 한다.** 새 계산을 만들 때 `activeRecords`를 빠뜨리면 취소한 기록이 섞인다. 그래서 테스트에 "취소된 기록은 빠지는지"를 꼭 넣는다
- **"취소 되돌리기"가 없다.** 잘못 취소했으면 원래 기록을 다시 입력한다

## 6. [수정] 버튼 (10단계, 2026-10-27)

10단계에서 이력 줄마다 [수정]이 생겼다. 개발자가 "왜 취소하고 다시 새기록을 쓰는거지?"라고 물어서 설명한 내용이다.

**아버지 눈에는 기록이 바뀐 것으로 보이지만, 폰 안에서는 1번 표처럼 ②취소와 ③새 기록이 한 번에 들어간다.** 원래 기록 ①은 그대로 있다.

### 기록을 직접 바꾸면 무엇이 안 되나

아버지와 형이 하우스에서 인터넷 없이 같은 기록(10월 25일 3동 약)을 각자 고쳤다고 해 보자.

```
기록을 직접 바꾸는 방식 (UPDATE)
  아버지 폰: 날짜를 10월 24일로 바꿈
  형 폰:     약 이름을 "나약"으로 바꿈
  → 인터넷이 이어지면 늦게 올린 쪽(형)이 그 줄을 통째로 덮어씀
  → 서버: 10월 25일, 나약   ← 아버지가 바꾼 날짜가 소리 없이 사라짐

이 앱 (INSERT만)
  아버지 폰: ①취소 + 10월 24일 가약
  형 폰:     ①취소 + 10월 25일 나약
  → 넷 다 서버에 올라감. ①은 취소됨, 새 기록 둘이 이력에 보임
  → 하나를 취소하면 끝. 아무것도 사라지지 않음
```

Java로 치면 낙관적 잠금(`@Version`) 없이 두 사람이 같은 엔티티를 `save()`한 것과 같다. 서버가 하나면 `@Version`으로 "누가 먼저 고쳤으니 다시 해 주세요"라고 막을 수 있지만, 이 앱은 폰이 인터넷 없이 따로 저장하므로 그 자리에서 막을 서버가 없다.

```java
// 직접 바꾸는 방식이라면: 마지막에 save한 쪽이 이긴다 (last write wins)
record.setWorkDate(LocalDate.of(2026, 10, 24));   // 아버지
repository.save(record);
record2.setPesticide("나약");                       // 형 (같은 id, 옛 날짜를 들고 있음)
repository.save(record2);                          // → 아버지의 날짜가 덮어써짐

// 이 앱: 원래 행은 건드리지 않는다
repository.save(new CancelRecord(newId(), 3, today, record.id()));
repository.save(new SprayRecord(newId(), 3, LocalDate.of(2026, 10, 24), "가약"));
```

그리고 지금 코드가 이미 이 방식에 맞춰져 있다.

- 서버 권한: 추가만 되고 수정·삭제는 아무도 못 한다 (`supabase/records.sql`)
- 내려받기: 폰에 없는 기록을 더한다 ([[2026-10-23-6단계-코드-읽기]] 9번)

직접 바꾸는 방식으로 가려면 이 둘과 "둘이 고치면 누구 것을 따를지(충돌 처리)"를 모두 새로 짜야 한다.

### 수정에서 지키는 것

| 규칙 | 이유 |
|---|---|
| 취소와 새 기록은 한 번에(트랜잭션) 넣는다 | 하나만 들어가면 기록이 사라지거나(취소만) 두 개가 된다(새 기록만) |
| 종류는 못 바꾼다 (약 → 관비 등) | 종류마다 칸이 달라서 바꾸면 새로 적는 것과 같다. 틀렸으면 취소하고 새로 적는다 |
| 수확 완료를 수정하면 그 수확량을 새 수확 완료에 옮긴다 | 수확량은 `target_id`로 수확 완료 기록을 가리킨다. 원래 수확이 취소되면 수확량도 계산에서 빠지기 때문이다 (3번 표) |
| 새 기록은 원래 기록의 입력 시각(`recorded_at`)을 이어받는다 | 아래 |

**입력 시각을 이어받는 이유.** 같은 날 기록끼리는 나중에 입력한 것이 "마지막 기록"이다 ([[2026-10-22-1단계-코드-읽기]] 3-2번 `isLater`).

```
같은 날 5동: 아침 08:00 수확 시작, 저녁 18:00 수확 완료 → "자라는 중"
다음 날 수확 시작을 열고 아무것도 안 바꾸고 저장
  지금 시각을 넣으면:  새 수확 시작 = 다음 날 09:00 입력 → 완료(18:00)보다 나중 → "수확 중" ✗
  원래 시각을 이어받으면: 새 수확 시작 = 08:00 → 완료보다 앞 → "자라는 중" 그대로 ✓
```

그래서 수정한 기록의 `recorded_at`은 "처음 입력한 시각"이다. 수정한 시각은 취소 기록에 남는다. 입력한 사람(`recorded_by`)은 수정한 사람이다.
